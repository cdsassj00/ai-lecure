Context Injection

리더와 기관을 위한 맥락주입 AI 방법론

행정안전부 AI챔피언 전문인재 보수교육 · 2026년 9월 8일

이 교재는 두 가지 독립된 주제를 다룹니다. 1부에서는 PowerShell, VBA, Python, Node.js, HTML·CSS·JavaScript를 이용해 서로 다른 업무 도구와 자동화를 만드는 방법을 배웁니다. 파일 정리, 엑셀 집계, 문서 일괄 처리, 계산기, 설문 서비스 등 활용 범위를 넓히는 것이 목표입니다.

2부에서는 AI가 답변할 때 필요한 자료를 제공하는 방법을 배웁니다. 문서를 직접 넣거나, 비정형 문서를 JSON·관계형 테이블·JSONB·XML로 준비하고 조회하거나, RSS·API·MCP를 통해 필요한 자료를 가져오는 방식을 비교합니다. 임베딩이나 벡터 데이터베이스 구축은 이 과정의 실습 대상이 아닙니다.

각 장은 원리, 구체적인 업무 사례, 실행 흐름과 확인할 결과를 설명합니다. 예제의 기관명·금액·사업·공고는 구조를 설명하기 위한 가상 자료입니다.

PART 1 · 다양한 방식의 바이브코딩

바이브코딩은 자연어로 요구를 설명하고 AI가 작성한 코드를 실행·수정하면서 원하는 결과물을 만드는 접근입니다. 결과물은 웹사이트일 수도 있고, 몇 줄짜리 파일 정리 스크립트나 엑셀 안의 버튼일 수도 있습니다.

이 부의 학습 목표는 업무에 맞는 구현 방식을 고르는 것입니다. 프로그램에 생성형 AI 기능이 들어갈 필요는 없습니다. AI와 함께 만든 견적서 계산기가 실행할 때에는 사칙연산만 하더라도 바이브코딩의 결과물입니다.

1장 AI로 코드를 만드는 일과 AI 기능을 넣는 일

개발 과정에서 사용하는 AI와 완성된 프로그램이 사용하는 AI는 구분해야 합니다. “폴더 안의 사진 이름을 날짜순으로 바꿔 줘”라고 요청해 코드를 만드는 동안에는 AI를 사용하지만, 완성된 코드는 날짜를 읽고 이름을 바꾸는 규칙만으로 작동할 수 있습니다.

반대로 민원 문장의 의도를 해석하거나 자유서술 의견을 요약하는 기능에는 실행 중 모델 호출이 필요할 수 있습니다. 이때에는 로컬 모델이나 모델 API를 별도로 연결해야 합니다. 코딩 도구를 구독했다고 완성된 앱의 모델 API 이용 권한과 비용까지 자동으로 포함되는 것은 아닙니다.

어떤 결과물을 원하는지부터 말한다

업무 장면, 입력, 처리, 출력, 실행 위치를 지정합니다. 예를 들어 “엑셀에서 선택한 표를 부서별 시트로 분리하고, 원본 시트는 유지하며, 버튼을 누르면 실행되게 해 줘”라고 설명합니다. 이 요청은 엑셀 안에서 수행하는 작업이므로 VBA가 자연스러운 후보입니다.

결과를 확인한 뒤 한 번에 한 가지씩 수정합니다. 실행 오류가 있으면 오류 메시지와 기대한 결과를 함께 전달합니다. 보기 좋은 화면과 정확한 계산은 별도로 확인합니다.

2장 PowerShell · 내 PC의 파일과 반복 작업

PowerShell은 명령을 실행하고 파일·폴더·프로세스 등을 다루는 셸이자 스크립트 언어입니다. Windows 작업에 자주 쓰이며, 별도로 설치하는 PowerShell 7은 다른 운영체제에서도 사용할 수 있습니다. 다만 Windows 전용 기능을 쓰는 스크립트가 다른 운영체제에서 그대로 작동하는 것은 아닙니다.

예를 들어 다운로드 폴더에서 PDF는 PDF 폴더로, 사진은 이미지 폴더로 분류하거나, 여러 폴더의 파일명을 일괄 변경하거나, 특정 프로그램을 정해진 순서로 실행할 수 있습니다. 이런 작업에는 별도의 웹사이트나 데이터베이스가 필요하지 않을 수 있습니다.

예제 · 파일명 일괄 변경

작업 흐름은 폴더 선택 → 대상 파일 확인 → 기존 이름과 변경할 이름의 미리보기 → 실행 → 결과 기록입니다. 처음부터 이동·삭제를 실행하기보다 변경 예정 목록을 먼저 보여 주면 사용자가 규칙을 확인하기 쉽습니다.

AI 요청 예시: “선택한 폴더의 PDF 파일 앞에 2026_를 붙이는 PowerShell 스크립트를 만들어 줘. 이미 접두어가 있으면 건너뛰고, 같은 이름이 있으면 덮어쓰지 마. 먼저 변경 예정 목록을 보여 줘.”

실행 환경은 PowerShell이며, 스크립트 파일은 보통 .ps1입니다. 기관의 실행 정책이 있는 경우 그 정책에 맞춰 실행합니다. 결과 확인은 전체 개수, 제외된 파일, 충돌한 이름과 실제 변경 목록으로 합니다.

3장 VBA · 엑셀과 Office 안에서 자동화

VBA는 Office 프로그램 안에서 문서·시트·셀 같은 객체를 다루는 언어입니다. 엑셀에 이미 있는 업무를 버튼 하나로 묶고 싶을 때 적합합니다. 여러 시트를 합치고, 부서별 보고서를 나누고, 일정한 인쇄 서식을 적용하는 기능이 대표적입니다.

예제 · 부서별 실적표 만들기

전체 실적 시트에서 부서명을 읽고 부서별 시트를 만든 뒤 합계를 계산하고 인쇄 영역을 설정합니다. 사용자는 익숙한 엑셀에서 버튼을 누릅니다. 결과물은 매크로를 보존하는 .xlsm 형식 등으로 저장해야 합니다.

AI 요청 예시: “현재 통합문서의 실적 시트를 부서 열 기준으로 나누는 VBA를 작성해 줘. 머리글을 각 시트에 복사하고 금액 합계를 넣어 줘. 원본 시트는 유지하고 기존 결과 시트를 처리할 방법을 먼저 설명해 줘.”

데스크톱 Office의 VBA 편집기에서 코드를 넣고 실행합니다. 매크로 실행 허용 여부는 사용 환경에 따라 다릅니다. 웹용 엑셀에서 데스크톱 VBA를 그대로 실행한다고 가정하면 안 됩니다.

검증은 원본 합계와 부서별 합계의 일치, 빈 부서명 처리, 숫자로 보이는 문자열 처리, 중복 시트명 처리로 합니다. “실행 완료” 메시지만으로 계산이 맞다고 판단하지 않습니다.

4장 Python · 파일을 넘나드는 처리와 분석

Python은 파일 처리, 데이터 분석, 문서 생성, 웹 요청, 간단한 데스크톱 도구 등 여러 작업에 사용할 수 있는 범용 언어입니다. 서로 다른 형식의 파일을 대량으로 처리할 때 특히 유용합니다.

예를 들어 여러 엑셀 파일을 합쳐 집계표를 만들거나, 사진 크기를 일괄 변경하거나, PPTX의 텍스트를 추출하거나, 수료증을 수백 장 생성할 수 있습니다. 작업별로 필요한 라이브러리는 다릅니다. Python을 설치했다고 모든 문서 형식을 바로 읽을 수 있는 것은 아닙니다.

예제 · 수료증 일괄 생성

명단 파일을 읽고 → 이름·과정명·날짜를 확인하고 → 양식에 값을 채우고 → 개인별 파일을 저장합니다. 파일명을 만드는 규칙과 동명이인 구분 방법도 정합니다.

AI 요청 예시: “명단 CSV와 수료증 양식을 선택하면 사람별 수료증 파일을 만드는 Python 프로그램을 만들어 줘. 필요한 라이브러리와 설치 명령을 먼저 알려 주고, 이름이 비어 있는 행은 별도 목록으로 남겨 줘.”

실행 환경은 Python이며 .py 파일로 저장할 수 있습니다. 처음에는 샘플 3명으로 결과를 확인한 뒤 전체 명단에 적용합니다. CSV 읽기처럼 표준 라이브러리로 가능한 작업과 Office·PDF 처리처럼 추가 도구가 필요한 작업을 나눠 봅니다.

5장 HTML·CSS·JavaScript · 브라우저에서 쓰는 도구

HTML은 화면의 내용과 구조, CSS는 모양과 배치, JavaScript는 계산과 동작을 담당합니다. 일상적으로 “HTML 도구를 만든다”고 부르지만 입력값에 따라 계산하거나 파일을 저장하는 기능에는 보통 JavaScript가 함께 들어갑니다.

견적서, 출장비 계산기, 체크리스트, 타이머, 좌석 배치 도구, 교육용 퀴즈 등을 단일 HTML 파일로 만들 수 있습니다. 외부 의존성이 없다면 파일을 더블클릭해 브라우저에서 실행하는 방식도 가능합니다.

예제 · 편집 가능한 견적서

품목·수량·단가 입력 → 공급가액과 세액 계산 → 인쇄 미리보기 → PDF 저장으로 구성합니다. 금액 계산은 JavaScript가 하고, A4 출력 모양은 CSS가 담당합니다.

AI 요청 예시: “품목 행을 추가·삭제할 수 있는 단일 HTML 견적서를 만들어 줘. 수량과 단가로 금액을 자동 계산하고, 인쇄할 때 버튼은 숨겨 줘. 입력값을 JSON 파일로 내보내고 다시 불러오게 해 줘.”

브라우저의 로컬 저장은 그 브라우저 환경에 묶일 수 있으므로 공유 DB처럼 생각하지 않습니다. 일반 웹페이지는 사용자 선택이나 권한 없이 PC의 모든 파일을 자유롭게 읽고 실행할 수 없습니다. API 비밀키를 배포할 HTML 안에 넣는 방식도 피해야 합니다.

6장 Node.js · JavaScript로 서버와 자동화 만들기

Node.js는 JavaScript를 브라우저 밖에서 실행하는 환경입니다. 화면 기술인 HTML과 역할이 다릅니다. 서버, 명령줄 도구, 파일 처리 스크립트와 외부 API 연결 프로그램 등을 만들 수 있습니다.

예제 · 여러 사람이 사용하는 설문

브라우저가 설문 화면을 보여 주고 사용자가 응답하면 서버로 전송합니다. Node.js로 만든 서버는 입력값을 확인하고 데이터베이스에 저장한 뒤 접수 결과를 돌려줄 수 있습니다. 관리자 화면은 같은 서버에서 집계 결과를 받아 표시합니다.

AI 요청 예시: “HTML 설문 화면과 Node.js 서버를 만들어 줘. 응답은 서버 쪽 SQLite에 저장하고 필수 항목 누락을 검사해 줘. 로컬에서 실행하는 설치 명령과 접속 주소를 설명해 줘.”

Node.js 설치와 프로젝트 의존성 설치가 필요할 수 있습니다. 로컬 실행은 내 PC에서 서버를 켜는 것이며, 다른 사람이 지속적으로 접속할 서비스라면 호스팅과 접근 설정이 추가로 필요합니다.

서버를 만들었다는 것과 공개 배포했다는 것은 다릅니다. 수업에서는 먼저 로컬에서 입력·저장·재조회가 되는지 확인하고, 공유가 필요할 때 실행 환경을 확장합니다.

7장 브라우저 확장과 데스크톱 프로그램

브라우저 확장은 기존 웹사이트 위에서 선택한 텍스트를 정리하거나, 반복 입력을 돕거나, 화면에 기능을 추가할 때 사용할 수 있습니다. 독립 웹페이지와 달리 확장 설정 및 접근할 사이트에 대한 권한 구성이 필요합니다.

데스크톱 앱은 파일 선택 창, 로컬 프로그램 실행, 운영체제 기능과의 연결이 필요한 경우의 선택지입니다. Electron 같은 환경에서는 HTML 기반 화면과 로컬 기능을 연결할 수 있습니다. Python으로 간단한 창을 만드는 방법도 있습니다.

예를 들어 “선택한 폴더의 이미지 크기를 일괄 변경하는 앱”은 화면에서 폴더를 받고 Python이나 Node.js 쪽 처리 코드가 파일을 변환하도록 구성할 수 있습니다. 각 기능이 어느 환경에서 실행되는지 정하는 것이 핵심입니다.

브라우저 화면만으로 충분한 계산기, 엑셀 안에서 편한 집계 매크로, PC 파일을 다루는 데스크톱 앱은 사용 장면이 다릅니다. 모든 업무를 하나의 웹서비스로 만들 필요는 없습니다.

8장 업무에 맞는 구현 방식을 고르는 실습

파일과 폴더를 반복 조작한다면 PowerShell, 엑셀 안의 표·서식·인쇄를 다룬다면 VBA, 여러 파일 형식의 처리와 분석은 Python, 브라우저 화면과 계산은 HTML·CSS·JavaScript, 서버와 공유 기능은 Node.js 등을 우선 비교할 수 있습니다. 이것은 전용 영역을 나누는 규칙이 아니라 시작점을 고르는 기준입니다.

실습에서는 자신의 반복 업무 한 가지를 고릅니다. “월별 파일 이름 정리”, “부서별 엑셀 분리”, “수료증 생성”, “견적서 자동 계산”, “설문 응답 저장” 중 하나를 선택해 입력·처리·출력을 작성합니다.

그다음 실행 환경과 결과 파일을 정하고 AI에게 최소 기능을 요청합니다. 처음에는 샘플 입력 하나로 실행한 뒤 빈 값, 중복 값, 잘못된 형식 등 예상 가능한 입력을 확인합니다.

이 부의 결과물은 업무에 맞는 작은 자동화나 도구입니다. 다음 부의 AI 맥락 제공 시스템을 만들기 위한 선행 프로젝트로 한정하지 않습니다.

PART 2 · Context Injection의 다양한 구현 사례

여기서 Context Injection은 AI가 답변하는 시점에 필요한 지침·사실·문서·조회 결과를 입력 맥락에 제공하는 실무적 의미로 사용합니다. 모델을 다시 학습시키는 작업과 구분됩니다.

문서를 직접 전달하는 방식, 문서를 구조화해 조회하는 방식, XML·RSS를 읽는 방식, API와 MCP로 외부 자료를 가져오는 방식이 있습니다. 자료 형식, 조회 방법, 연결 규약은 서로 다른 층위이며 하나의 시스템에서 함께 사용될 수 있습니다.

예를 들어 문서를 JSON으로 추출해 PostgreSQL의 JSONB에 저장하고, SQL로 조건을 조회한 뒤, API 또는 MCP로 결과를 AI에게 전달할 수 있습니다. 이 과정에 벡터 데이터베이스가 필수인 것은 아닙니다.

1장 맥락을 제공한다는 것은 무엇인가

사용자가 “A사업의 신청 서류가 뭐야?”라고 물었다고 가정합니다. 모델이 해당 공고를 입력으로 받지 못했다면 현재 공고 내용을 근거로 답한다고 보장할 수 없습니다. 프로그램이 공고문이나 조회 결과를 가져와 질문과 함께 모델에 넣으면 그 자료를 바탕으로 답하도록 할 수 있습니다.

공통 흐름은 질문을 받기 → 필요한 자료를 읽거나 조회하기 → 결과와 출처를 입력에 포함하기 → 모델이 답변하기입니다. 자료를 미리 전부 넣을 수도 있고, 질문이 생겼을 때 필요한 것만 가져올 수도 있습니다.

“바로 대답한다”는 말은 별도의 임베딩 색인을 구축하지 않고 원문·DB·API 등의 결과를 그때 가져와 답한다는 뜻으로 이해할 수 있습니다. 실제로는 조회와 모델 호출의 단계가 있으며 네트워크나 처리 시간이 필요합니다.

용어상 검색 결과를 이용한 생성은 넓은 의미의 RAG라고 부를 수도 있습니다. 이 교재에서는 그 명칭 논쟁보다 벡터 검색 없이 자료를 준비하고 전달하는 구체적인 방법을 중심으로 설명합니다.

2장 먼저 형식·조회·연결을 구분한다

JSON과 XML은 데이터를 표현하는 형식입니다. 관계형 테이블은 행과 열로 저장하는 구조이고, SQL은 데이터베이스에 질의하는 언어입니다. JSONB는 이 교재에서는 PostgreSQL이 JSON 데이터를 처리·저장하는 자료형을 뜻합니다.

RSS는 새 소식이나 항목 목록을 배포하는 XML 기반 형식입니다. 모든 XML이 RSS인 것은 아닙니다. 문서의 조문·항목·조건을 담는 사용자 정의 XML을 따로 만들 수도 있습니다.

API는 프로그램이 데이터를 요청하고 결과를 받는 접점입니다. MCP는 AI 애플리케이션과 외부 도구·자료를 연결하는 표준 규약입니다. API와 MCP의 뒤쪽에서 SQL 조회나 RSS 읽기를 수행할 수도 있습니다.

따라서 “JSONB와 MCP 중 무엇이 더 좋은가”보다 “JSONB에 저장한 자료를 어떤 조건으로 조회하고 MCP로 어떻게 제공할 것인가”가 적절한 설계 질문입니다.

3장 문서·텍스트를 직접 제공하는 방식

자료가 짧고 대상이 명확하면 필요한 문장을 질문과 함께 직접 넣습니다. 예를 들어 공고문의 신청 자격·제출 서류·마감일 부분을 붙여 넣고 “이 내용으로 안내문을 작성해 줘”라고 요청할 수 있습니다.

파일을 읽는 프로그램을 만든다면 PDF·DOCX·텍스트 등의 내용을 추출한 후 모델 입력에 포함합니다. 스캔 문서는 OCR이 필요할 수 있고, 표나 각주는 일반 본문 추출에서 누락될 수 있어 확인해야 합니다.

앱의 파일 첨부 기능이 내부적으로 원문 전체를 넣는지 일부를 검색하는지는 앱 구현에 따라 다릅니다. 직접 만든 방식에서는 실제 모델에 전달한 텍스트를 확인해 어떤 근거가 들어갔는지 알 수 있습니다.

장점은 별도 DB 설계 없이 시작할 수 있다는 것입니다. 한계는 길이·반복 전송 비용·갱신 관리입니다. 문서가 길어질 때에는 사용자가 필요한 절을 지정하거나 목차·문서 ID로 필요한 부분만 읽는 방법을 사용할 수 있습니다.

적용 사례 · 암묵지를 데이터화해 맥락으로 제공한다

Context Injection에 사용할 근거는 이미 존재하는 문서나 DB에만 한정되지 않습니다. 숙련자의 경험, 인수인계 때 말로 전달하는 주의사항, 실제 처리 과정의 판단 기준을 기록하는 일도 자료 준비에 포함됩니다.

가상 사례로 담당자가 “이 유형의 민원은 접수 전에 시설 담당자와 먼저 확인해야 한다”고 설명했다고 가정합니다. 이 문장만 저장하면 적용 범위를 알 수 없습니다. 어떤 유형인지, 무엇을 확인하는지, 왜 필요한지, 확인 결과에 따라 다음 행동이 어떻게 달라지는지 질문합니다.

인터뷰나 업무 시연을 기록하고 “상황, 판단 기준, 확인 항목, 조치, 예외, 근거, 검토자, 확인일”로 정리합니다. 처음에는 문서나 표로 작성해도 됩니다. AI가 전사와 초안을 도울 수 있지만 당사자가 실제 경험과 일치하는지 확인해야 합니다.

공식 규정과 경험적 조언을 구분합니다. 특정 상황에서 통했던 방법을 모든 상황에 적용하는 규칙으로 바꾸지 않도록 적용 조건과 한계를 보존합니다. 말로 설명하기 어려운 감각은 여러 사례와 반례를 통해 일부를 구체화할 수 있으며 모든 암묵지가 완전히 데이터화된다고 가정하지 않습니다.

검토된 기록은 작은 문서로 직접 모델에 넣거나 JSON·JSONB에 저장합니다. 질문에 해당하는 상황을 조회해 원문 기록과 함께 제공하고, 답변에는 “경험에 기반한 참고사항”과 “공식 기준”을 구분해 표시합니다. 이것도 Context Injection의 하나의 구현 사례입니다.

4장 비정형 문서를 사전 분석해 JSON으로 만든다

사전 구조화는 긴 문서를 읽고 반복해서 사용할 항목을 이름 붙여 저장하는 작업입니다. 공고문에서 사업명, 대상, 신청 기간, 제출 서류, 담당 부서를 추출하면 매번 문서 전체를 다시 해석하지 않고 필요한 항목을 가져올 수 있습니다.

{"id":"A01","사업명":"가상 A사업","제출서류":["신청서","계획서"],"마감일":"2026-09-30","출처":"공고문.pdf","쪽":3}

진행 순서는 원문 텍스트 추출 → 항목 정의 → 규칙이나 AI로 값 추출 → 사람이 표본 대조 → JSON 저장입니다. 항목 정의를 스키마라고 합니다. 날짜 형식과 목록 형식 등을 통일하면 이후 조회가 쉬워집니다.

요약문 하나만 저장하면 예외·제외 조건을 잃기 쉽습니다. 추출값 외에 원문 발췌와 위치도 보관하고, 찾지 못한 값은 임의로 채우지 않습니다. 본문과 별첨의 조건이 다르면 그 관계도 남깁니다.

질문 시 프로그램은 id가 A01인 객체를 고르고 제출서류 값을 읽어 모델에 전달할 수 있습니다. JSON으로 저장했다는 사실만으로 자동 검색이나 맥락 전달이 생기는 것은 아닙니다. 이를 수행하는 코드가 있어야 합니다.

5장 관계형 테이블로 저장하고 SQL로 조회한다

여러 문서에서 같은 항목을 반복 추출하고 날짜·금액·부서별 조건을 정확하게 걸고 싶다면 관계형 테이블이 적합합니다. 예를 들어 사업 테이블에 사업 ID, 사업명, 마감일, 부서를 저장하고 제출 서류는 별도 테이블에 사업 ID와 함께 저장합니다.

SELECT title, deadline, source
FROM programs
WHERE department = :department
  AND deadline >= :as_of
ORDER BY deadline;

이 예시는 프로그램이 department와 as_of 값을 전달하는 매개변수 질의입니다. 실제 자리표시자 문법은 사용하는 DB 드라이버에 맞춥니다. “아직 접수 중인 교육부서 사업”이라는 질문에서 부서와 기준일을 정해 조회하고, 반환된 행을 모델에 전달합니다.

합계·개수·평균은 SQL이나 일반 코드로 계산하고 모델은 계산된 결과를 설명하게 할 수 있습니다. 숫자 계산을 긴 본문에서 모델이 추측하게 할 필요가 없습니다.

자연어 질문마다 AI가 SQL을 자유롭게 만들게 할 수도 있지만 필수는 아닙니다. 초기에 몇 가지 고정 조회 함수를 만들고 부서·날짜 같은 인자만 채우는 방식이 더 단순합니다. 어느 방식이든 조회 권한과 결과 범위를 프로그램에서 제한합니다.

6장 JSONB · 문서마다 다른 항목을 DB에 보관한다

문서 종류마다 항목이 조금씩 다르면 공통 정보는 일반 열에, 문서별 세부 항목은 JSONB 열에 둘 수 있습니다. 예를 들어 id와 문서 종류는 열로 두고 지원 대상·예외·제출 서류는 payload라는 JSONB 열에 저장합니다.

SELECT id, payload->'제출서류' AS documents
FROM notices
WHERE payload->>'사업명' = '가상 A사업';

이 PostgreSQL 예시는 JSONB 안에서 사업명이 일치하는 자료를 찾아 제출 서류 목록을 돌려줍니다. 결과를 보통 JSON이나 텍스트로 직렬화해 모델에 전달합니다. 모델에 DB 내부의 바이너리를 직접 넣는다는 뜻은 아닙니다.

JSON 파일은 프로그램이 파일을 읽어 처리하는 시작점이고, JSONB는 DB 안에서 여러 문서의 구조화 값을 질의할 수 있게 하는 선택지입니다. 데이터가 많아지면 조회 조건에 맞춰 인덱스를 설계할 수 있습니다.

정해진 숫자·날짜를 집계하는 데에는 일반 열이 편하고, 문서별 가변 항목에는 JSONB가 편할 수 있습니다. 둘을 혼합할 수 있으며 JSONB로 바꾼다고 문서 해석의 정확도가 자동으로 높아지지는 않습니다.

7장 XML · 문서의 계층과 항목을 표현한다

XML은 시작·종료 태그로 데이터의 구조를 표현합니다. 조문 아래 항, 항 아래 호처럼 문서의 계층을 남기거나 기존 시스템의 XML 응답을 읽을 때 사용할 수 있습니다.

<notice id="A01">
  <title>가상 A사업</title>
  <documents><item>신청서</item><item>계획서</item></documents>
  <source page="3">공고문.pdf</source>
</notice>

질문 시에는 XML 파서로 notice의 id를 찾고 documents 아래 item 값을 꺼냅니다. 필요한 항목과 출처만 텍스트나 JSON으로 바꾸어 모델에 전달하거나, 작은 XML 조각을 그대로 전달할 수도 있습니다.

문서 전체를 태그 하나 안에 넣는 것만으로 항목별 조회가 쉬워지지는 않습니다. 사업·조건·예외처럼 의미 있는 경계를 설계해야 합니다. XML의 네임스페이스가 있는 응답에서는 파서도 그 네임스페이스를 처리해야 합니다.

JSON과 XML 중 모델이 무조건 더 잘 이해하는 형식이 정해져 있는 것은 아닙니다. 기존 자료 형식, 계층 표현, 코드 처리 편의와 입력 크기를 기준으로 선택합니다.

8장 RSS XML · 갱신되는 소식을 읽어 제공한다

RSS는 제목·링크·설명 등 항목을 XML로 배포하는 방식입니다. 발행처의 RSS URL을 HTTP로 요청하고 항목을 읽어 AI에게 제공할 수 있습니다. RSS 읽기 자체에 벡터 DB는 필요하지 않습니다.

<rss version="2.0"><channel><title>가상 기관 소식</title>
<link>https://example.org</link><description>새 소식</description>
<item><title>A사업 공고</title><link>https://example.org/a</link>
<description>신청 안내 요약</description></item>
</channel></rss>

흐름은 RSS 요청 → XML 파싱 → 날짜·제목·키워드로 항목 선택 → 설명과 출처 전달 → 답변입니다. 최근 항목을 미리 수집해 두는 방식과 질문할 때 읽는 방식 모두 가능합니다.

피드에 요약만 있으면 AI도 요약 수준의 정보만 받습니다. 제출 서류처럼 본문에만 있는 내용은 링크의 원문을 추가로 가져오거나 원문 확인이 필요하다고 표시해야 합니다. RSS 주소를 안다고 모든 과거 자료를 볼 수 있는 것도 아닙니다.

날짜와 고유 ID는 제공되는 경우 활용하고, 수집시각은 별도로 남깁니다. 새로 요청했다는 사실과 발행처 데이터가 최신이라는 사실을 구분합니다. 동일 항목 중복, 피드 실패, 본문 미포함 상황을 처리합니다.

9장 API 직접 호출 · 필요한 데이터를 그때 받는다

API 방식은 프로그램이 외부 또는 내부 시스템에 조건을 보내 필요한 결과를 받는 방법입니다. 예를 들어 사업 조회 API에 사업 ID를 보내면 신청 기간과 제출 서류가 JSON으로 반환되도록 만들 수 있습니다.

요청 예시: GET /api/programs/A01
응답 예시: {"id":"A01","제출서류":["신청서","계획서"],"source":"공고문.pdf"}

직접 만든 웹앱에서는 질문을 받은 백엔드가 API를 호출하고 응답을 정리한 뒤 모델 입력에 넣습니다. 고정된 업무라면 모델이 도구를 고르게 할 필요 없이 프로그램이 먼저 조회해도 됩니다.

다른 방법은 모델에 “사업조회” 도구의 이름·설명·입력 규칙을 알려 주고 호출 요청을 받는 것입니다. 실제 HTTP 요청은 애플리케이션이 실행하고, 그 결과를 다시 모델에게 보내 답변을 받습니다. 일반적으로 이를 도구 호출 또는 함수 호출 흐름이라고 합니다.

API가 반환하는 오류, 빈 결과, 페이지 구분, 조회 제한을 처리합니다. 데이터가 여러 페이지라면 첫 페이지만 받고 전체라고 설명하지 않아야 합니다. 인증 정보는 서버에서 관리하고 사용자 화면에는 필요한 결과만 전달합니다.

10장 MCP 서버·클라이언트로 자료를 제공한다

MCP에서는 AI 앱인 호스트 안의 클라이언트가 MCP 서버와 통신합니다. 서버는 도구나 자료를 제공하고, 호스트는 필요한 결과를 모델의 맥락에 넣습니다. MCP 서버 자체가 곧 언어모델이거나 최종 답변 생성기는 아닙니다.

예를 들어 서버에 get_program이라는 도구를 만들고 입력값으로 program_id를 받게 합니다. 서버 내부에서는 SQL 조회, JSON 파일 읽기, XML 파싱 또는 기존 API 호출 중 적합한 방법을 실행합니다.

질문에서 답변까지

① 사용자가 AI 앱에 A사업의 서류를 묻습니다. ② 호스트가 제공한 도구 정보를 바탕으로 모델이 get_program 호출을 요청합니다. ③ 호스트의 MCP 클라이언트가 서버로 요청합니다. ④ 서버가 자료를 조회해 결과와 출처를 반환합니다. ⑤ 호스트가 그 결과를 모델에 넣습니다. ⑥ 모델이 서류를 설명합니다.

도구는 매개변수를 받아 작업을 수행하는 인터페이스이고, 리소스는 URI로 식별되는 자료를 제공하는 인터페이스입니다. 앱은 리소스를 읽어 맥락에 넣을 수도 있습니다. 어떤 기능을 실제로 노출하고 활용하는지는 클라이언트 구현에 따라 다릅니다.

이미 만든 API를 MCP 서버 안에서 호출하도록 감쌀 수 있습니다. MCP를 붙이면 벡터 검색이 자동으로 생기거나 DB가 자동 연결되는 것은 아닙니다. 서버에 조회 기능을 구현하고 호스트에 연결을 구성해야 합니다.

11장 내 웹앱에 MCP를 연결하는 구성

자신이 만든 웹앱에서도 MCP를 사용할 수 있습니다. 화면은 질문과 답변을 보여 주고, 백엔드는 모델 호출과 MCP 클라이언트를 담당하고, MCP 서버는 실제 데이터를 조회하게 구성할 수 있습니다.

구성 예시는 HTML 화면 → 내 백엔드의 모델 호출·MCP 클라이언트 → MCP 서버 → JSONB 데이터베이스입니다. 모델이 도구 사용을 요청하면 백엔드가 MCP 호출을 실행하고 도구 결과를 다음 모델 입력에 포함합니다.

먼저 AI 없이 서버의 조회 결과가 맞는지 확인합니다. 다음으로 MCP 클라이언트가 도구 목록과 호출 결과를 받는지 확인하고, 마지막으로 모델이 그 결과를 근거로 답하는지 확인합니다. 이렇게 하면 데이터 조회 오류와 모델 설명 오류를 구분할 수 있습니다.

한 앱에서 정해진 API만 호출한다면 직접 API 연결로 충분할 수 있습니다. 동일한 조회 기능을 여러 MCP 지원 AI 앱에서 재사용하려는 경우에는 MCP 구성이 유용합니다. 모든 클라이언트가 같은 전송 방식과 기능을 지원한다고 가정하지 않습니다.

적용 사례 · 내 데이터와 사이트를 API·MCP로 제공한다

Context Injection 시스템은 외부 데이터를 가져오는 소비자이면서, 내가 가진 근거를 다른 AI에게 제공하는 공급자가 될 수도 있습니다. 사이트에 조회 API를 만들거나 DB·JSON·XML을 읽는 MCP 서버를 만들면 내가 만든 자료를 다른 앱의 답변 맥락으로 사용할 수 있습니다.

가상 설문 사이트를 예로 들면 설문 목록, 응답 집계, 주관식 응답을 읽는 기능을 정의합니다. API는 설문 ID를 받아 DB 조회 결과를 반환합니다. API 응답을 받은 AI 앱은 그 결과를 모델에게 전달해 분석 설명을 생성합니다. 사이트의 화면을 그대로 읽게 하는 것과 별개로 데이터 제공 기능을 구현하는 것입니다.

MCP 서버에서는 get_survey_summary 같은 도구에 설문 ID를 받게 하고, 서버가 직접 DB를 조회하거나 기존 API를 호출해 집계를 반환하게 할 수 있습니다. 기존 API가 필수인 것은 아닙니다. JSON 파일을 읽거나 XML의 특정 항목을 파싱하는 코드도 MCP 도구 뒤에서 실행할 수 있습니다.

자료 자체를 URI로 식별해 읽도록 제공하려면 MCP 리소스를 활용할 수 있습니다. 어떤 도구나 리소스가 사용자 질문에 활용되는지는 연결한 호스트·클라이언트 구현에 따라 달라집니다. 파일을 MCP라는 형식으로 변환하는 것이 아니라 자료에 접근하는 기능을 표준 인터페이스로 제공하는 것입니다.

내 사이트가 MCP를 이용하는 경우에는 백엔드의 클라이언트가 외부 MCP 서버를 호출합니다. 내 사이트의 자료를 MCP로 제공하는 경우에는 외부 AI 앱의 클라이언트가 내 MCP 서버를 호출합니다. 방향은 다르지만 두 경우 모두 반환된 자료가 모델의 입력에 들어갈 때 답변 근거가 됩니다.

공개 사이트를 만들었다고 API나 MCP가 자동으로 생기는 것은 아닙니다. 제공할 기능과 입력·출력 구조를 구현하고, 공개 가능한 범위와 사용자별 조회 권한을 적용합니다. 처음에는 설문 집계처럼 목적이 명확한 조회 기능 하나를 제공하는 것으로 시작할 수 있습니다.

12장 저장하지 않고 가져오기와 미리 저장하기

질문할 때 원본 API나 RSS를 요청하면 별도 복제 저장소 없이 시작할 수 있습니다. 원본 서비스의 응답 속도·가용성·제공 범위에 영향을 받으며 과거 이력은 별도로 제공되는 경우에만 조회할 수 있습니다.

반대로 문서를 미리 JSON이나 DB로 구조화하면 반복 질문을 빠르게 처리하고 여러 문서의 값을 비교할 수 있습니다. 대신 원문이 바뀌었을 때 재수집·재추출·갱신하는 절차가 필요합니다.

혼합 방식도 가능합니다. 사업 기본 정보는 DB에 저장하고 현재 접수 상태는 API로 확인합니다. 이때 저장 데이터의 기준일과 API 확인시각을 구분해 답변에 표시합니다.

선택 기준은 질문 빈도, 최신성 요구, 원본 접근 가능성, 이력 필요 여부와 전처리 비용입니다. 즉시 조회가 항상 더 정확하거나 사전 저장이 항상 더 오래된 정보를 준다고 단정하지 않습니다.

13장 구조화되지 않은 본문을 키워드로 찾는 보조 방식

모든 내용을 미리 항목으로 추출하기 어려우면 원문 본문을 보존하고 문서명·문서 ID·정확한 단어로 필요한 부분을 찾을 수 있습니다. 간단한 문자열 검색이나 전문검색 기능이 여기에 해당합니다.

예를 들어 회의록에서 “주차장”이 포함된 문단을 찾고 날짜와 회의명을 함께 반환합니다. SQL의 조건 조회로 회의 연도를 먼저 좁힌 뒤 본문 검색을 할 수도 있습니다. 이런 조회에 임베딩이 반드시 필요한 것은 아닙니다.

다만 질문의 “차량 주차 문제”와 원문의 다른 표현을 자동으로 같은 의미로 찾는 데에는 한계가 있습니다. 동의어 목록, 표준 용어, 문서 분류를 활용할 수 있습니다. 이 장은 본문을 가져오는 보조 선택지를 설명하며 별도의 벡터·하이브리드 검색 과정으로 확대하지 않습니다.

14장 조회 결과를 실제 모델 입력으로 만드는 방법

자료를 저장하거나 API에서 받아 오는 것과 모델에 전달하는 것은 별개의 단계입니다. 프로그램은 조회 결과 중 질문에 필요한 값·원문·출처·기준일을 선택해 모델이 읽을 입력으로 만들어야 합니다.

답변 지침: 제공된 근거로 답하고 없는 내용은 확인 필요로 표시.
질문: A사업의 제출 서류는?
근거: A01 / 제출서류: 신청서, 계획서
출처: 공고문.pdf 3쪽 / 자료 기준일: 2026-09-01

여러 자료가 있으면 자료별 ID를 붙이고 최종 답변이 어떤 ID를 참조하는지 연결합니다. 조회 결과가 비어 있는 경우에는 “필요한 근거를 찾지 못했다”고 안내할 수 있어야 합니다.

외부 문서 본문은 근거 데이터로 다룹니다. 그 안에 지시문처럼 보이는 문장이 있어도 앱의 실행 규칙으로 승격하지 않습니다. 입력에 자료와 지시의 경계를 명확히 두고, 실행 권한은 앱에서 관리합니다.

컨텍스트의 길이를 줄이는 핵심은 JSON이나 XML로 이름만 바꾸는 것이 아니라 필요한 항목을 골라 넣는 것입니다. 형식 선택만으로 토큰 절약과 답변 정확도를 보장하지 않습니다.

15장 같은 질문을 네 가지 구성으로 비교한다

공통 질문은 “가상 A사업의 제출 서류는 무엇인가?”입니다. 정답 근거는 공고문 3쪽의 신청서와 계획서이며, 조건과 예외가 있다면 함께 보존합니다.

구성 A: 공고문 해당 페이지의 텍스트를 직접 모델에 전달합니다. 문서가 소수일 때 간단합니다. 구성 B: 문서를 사전 추출한 JSON에서 A01을 읽어 제출서류와 출처를 전달합니다. 반복 질문에서 원문 해석을 줄입니다.

구성 C: 관계형 테이블이나 JSONB에서 A01을 SQL로 조회하고 결과를 전달합니다. 여러 사업 비교와 조건 조회로 확장할 수 있습니다. 구성 D: API 또는 MCP 도구에 A01을 요청하고 응답을 맥락에 넣습니다. 기존 업무 시스템이나 여러 AI 앱과 연결할 수 있습니다.

RSS는 새 공고의 발견과 요약에 사용할 수 있지만 피드에 제출 서류가 없다면 이 질문의 충분한 근거가 되지 않습니다. 원문을 추가 조회해야 합니다. 자료를 가져오는 통로와 그 자료가 질문에 충분한지는 따로 판단합니다.

16장 하루 프로젝트 · 나의 자료에 맞는 경로 하나

프로젝트는 답할 질문 세 개와 샘플 문서 또는 API 하나를 고르는 것에서 시작합니다. 가능한 예시는 공고문 제출 서류 안내, 회의록의 결정 사항 조회, 사업별 수치 비교, RSS 기반 기관 소식 정리입니다.

자료 형식과 전달 경로를 따로 기록합니다. 예를 들어 “PDF를 JSON으로 추출해 파일에 저장하고 사업 ID로 읽어 모델에 전달” 또는 “기존 API를 MCP 도구로 제공하고 지원 앱에서 질문”이라고 작성합니다.

작업 순서는 샘플 근거와 예상 답 작성 → 조회 기능 만들기 → 실제 전달 맥락 확인 → 답변 연결 → 출처 표시입니다. 한 번에 SQL·JSONB·XML·RSS·API·MCP를 모두 구현할 필요는 없습니다.

완료 기준은 정상 질문에 대한 근거 일치, 없는 항목의 미확인 처리, 변경된 자료의 반영 여부, 출처로 원문을 다시 찾을 수 있는지입니다. 검색창이 열린다는 사실만으로 완료로 판단하지 않습니다.
