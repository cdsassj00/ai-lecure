AI 프렌즈 발대식 특강EXECUTIVE SUMMARY
한 장 결론

AI 프렌즈의 목표는 현장의 작은 병목을 검증 가능한 AI 산출물로 바꾸는 것입니다.

거대한 시스템을 한 번에 만드는 것이 아니라, 현장에서 실제로 쓰이는 작은 서비스를 완성합니다.

왜 — WHY

병목은 플랫폼 밖에 있습니다

대형 시스템 구축이 끝나도 반복 취합, HWP 정리, 민원 분류, 점검보고서 작성 같은 골목길 문제는 남습니다. 이 문제는 기후·에너지·환경 현장을 아는 여러분만 풀 수 있습니다.

예: 매주 3시간 걸리는 17개 시·도 엑셀 취합 · 같은 5개 질문이 반복되는 악취 민원 · 이틀 걸리는 현장 점검 보고

무엇을 — WHAT

PoC와 MVP를 만듭니다

PoC는 본 사업 전 리스크를 줄이는 작은 실험, MVP는 사용자가 실제로 써볼 수 있는 최소 기능 버전입니다. 최종 산출물은 발표자료가 아니라 작게라도 쓰이는 AI 서비스입니다.

목표 경로: 2주 안에 PoC 1개 → 중간점검 때 동료 시연 → 종료 시 동료가 쓰는 MVP 1개

어떻게 — HOW

블록을 엮습니다(오케스트레이션)

Prompt · 문서 · Data · RAG · Python · API · DB · MCP · 사람 검토를 업무 흐름에 맞게 조합합니다. 모든 코드를 직접 짜는 사람이 아니라, 조합을 설계하는 사람이 필요합니다.

예: 같은 민원 문제도 "문서+RAG 답변기"와 "Python 자동 분류기"로 전혀 다르게 풀립니다

AI 프렌즈는 큰 AI를 기다리는 사람이 아니라, 현장의 작은 문제를 듣고 LLM·문서·데이터·도구·사람의 판단을 엮어 작게 쓰이는 서비스를 만드는 AI 오케스트레이터입니다.
오늘 특강 전체를 관통하는 문장 — 이후 모든 슬라이드는 이 문장의 근거입니다02
결론을 먼저 말씀드리겠습니다. AI 프렌즈의 목표는 거대한 시스템이 아니라 현장의 작은 병목을 검증 가능한 산출물로 바꾸는 것입니다. 왜냐하면(WHY) 반복 취합, HWP 정리, 민원 분류 같은 병목은 플랫폼이 완성돼도 남기 때문입니다. 그래서 만들 것은(WHAT) PoC와 MVP이고, 방법은(HOW) 블록을 엮는 오케스트레이션입니다. 이후 모든 슬라이드는 이 한 장의 근거입니다.

첫 번째 파트입니다. AI는 답변을 생성하는 도구에서 업무를 실행하는 구조로 이동하고 있습니다. 아래 흐름 — LLM, Agent, Workspace, Harness, Tool Calling — 이 다섯 단어가 이번 파트에서 다룰 전부입니다. 여러분은 이 변화를 구경하는 것이 아니라, 실제 업무 문제로 직접 구현해보게 됩니다.
PART 1 · AI 에이전트 시대LLM ALONE
LLM의 본질

LLM은 글을 쓰고 읽는 언어 엔진입니다.

답변은 잘하지만, 그것만으로는 아직 업무가 아닙니다.

LLM이 이미 잘하는 것

쓰기보도자료 초안, 답변 문안, 보고서 문장
읽기법령·지침·회의록 이해, 긴 문서 요약
추론비교, 정리, 기준에 따른 판단 보조
변환표↔문장, 한↔영, 형식 바꾸기

LLM 단독으로는 못 하는 것

파일 열기내 PC의 HWP·엑셀·PDF를 직접 열고 저장
계산·실행1만 행 엑셀 집계, 스크립트 실행
시스템 접속내부 업무시스템·DB 조회와 입력
최신·내부 자료오늘의 공지, 우리 부처 지침 반영
반복 수행매주 같은 취합을 사람 없이 반복
LLM은 두뇌에 가깝습니다. 실제 업무가 되려면 손(실행), 눈(자료), 책상(작업공간), 도구함(API·Python), 기록장(DB)이 붙어야 합니다.
근거: LLM Agent Harness Flow — "답변은 가능, 직접 실행은 아직 아님"05
먼저 LLM의 본질입니다. 왼쪽처럼 쓰기·읽기·추론·변환은 이미 잘합니다. 그런데 오른쪽을 보십시오. 내 PC의 HWP를 열지 못하고, 1만 행 엑셀을 집계하지 못하고, 내부 시스템에 접속하지 못하고, 매주 같은 취합을 스스로 반복하지 못합니다. LLM은 두뇌입니다. 손과 눈과 책상과 도구함과 기록장이 붙어야 업무가 됩니다. 무엇을 붙이는지가 다음 장입니다.
PART 1 · AI 에이전트 시대LLM + BLOCKS
업무가 되는 조건

업무가 되려면 LLM에 Web · 문서 · 지침 · 하네스 · Python · API · 데이터 · DB · MCP가 붙어야 합니다.

LLM에 붙이는 것맡는 역할기후·에너지·환경 업무 예시
+ Web 검색최신 정보와 공개 자료 접근오늘자 배출권 시세, 타 부처 보도자료, 해외 규제 동향 확인
+ 문서 · 지침우리 조직의 기준과 근거를 답변에 반영환경 법령, 내부 SOP, 업무편람을 근거로 한 답변 초안
+ 하네스(실행 PC)내 PC의 파일·프로그램·도구를 안전하게 호출Claude Code류 도구가 폴더 안 HWP·엑셀을 직접 읽고 수정
+ Python계산, 파일 변환, 반복 자동화 스크립트50개 기관 제출 엑셀을 한 번에 병합·집계·검증
+ API외부 서비스·시스템과 데이터 주고받기공공데이터포털 대기질 API, 기상청 API 호출
+ 데이터 · DB결과를 저장하고 다음 작업에서 다시 사용민원 분류 결과 축적, 시설 점검 이력 조회
+ MCPAI가 도구·데이터·서비스를 표준 방식으로 직접 호출내부 문서검색·일정·업무시스템을 AI가 도구처럼 사용
근거: hyperframe_llm_harness_flow v3 — 내부 도구(Python·Files·Excel·PDF·Browser) / 외부 도구(Web·API·SaaS) 호출 구조06
이 표의 일곱 줄이 오늘 기술 내용의 사실상 전부입니다. Web은 최신 정보, 문서·지침은 우리 조직의 기준, 하네스는 내 PC에서의 실행 환경, Python은 반복 자동화, API는 외부 연결, DB는 기억, MCP는 표준 호출 방식입니다. 오른쪽 열처럼 전부 기후·에너지·환경 업무로 번역됩니다. 여러분 팀의 과제도 결국 이 중 두세 개의 조합입니다.
PART 1 · AI 에이전트 시대AGENT HARNESS FLOW
에이전트는 모델 하나가 아니라 실행 구조

에이전트 = LLM + 도구 + 실행환경 + 검증 루프. 여섯 단계가 하나의 흐름으로 연결됩니다.

STEP ①

LLM

텍스트 이해 · 추론 · 답변 생성. 여기까지는 챗봇입니다.

STEP ②

Agent Loop

계획 → 도구 호출 → 결과 관찰 → 수정. Tool + Loop가 붙으면 에이전트가 됩니다.

STEP ③

내 PC Workspace

작업공간이 내 PC로 들어옵니다. IDE · Terminal · Browser · 파일시스템.

STEP ④

Harness 연결

권한 · 실행 · 결과 반환을 관리하는 연결 장치. tool call ↔ result.

STEP ⑤

내부 도구 호출

Python, 파일, Excel · PDF, 브라우저 등 내 PC 안의 도구 실행.

STEP ⑥

외부 도구 호출

Web, 외부 사이트, API, SaaS를 호출하고 결과를 다시 루프로.

여러분에게 의미

개발자가 되라는 뜻이 아닙니다. 이 구조를 알면 "AI에게 어느 단계에서 무엇을 맡기고, 사람이 어디서 승인할지"를 설계할 수 있습니다. 그것이 과제 설계의 출발점입니다.

설계 질문 3개 — ① AI가 맡는 단계는 어디인가 ② 사람 승인 지점은 어디인가 ③ 틀렸을 때 되돌리는 방법은 무엇인가

하네스 한 줄 정의

하네스는 AI가 실제 파일 · 프로그램 · 데이터 · 도구를 안전하게 호출하도록 연결하는 실행 환경입니다. 쉽게 말해 LLM이 업무 책상 위에서 손을 쓰게 만드는 구조입니다.

예: Claude Code · Codex CLI가 허용된 폴더 권한 안에서만 HWP·엑셀·PDF를 읽고 수정하고 기록을 남깁니다

근거: LLM Agent Harness Flow v3 — "LLM은 생각하고, Agent는 반복하고, Harness는 연결한다"07
여섯 단계가 에이전트의 실체입니다. LLM이 생각하고, Agent 루프가 계획·호출·관찰·수정을 반복하고, 작업공간이 내 PC로 들어오고, 하네스가 권한과 실행을 관리하며, 내부 도구와 외부 도구를 호출합니다. 개발자가 되시라는 말이 아닙니다. AI에게 어느 단계를 맡기고 사람이 어디서 승인할지 설계하는 것 — 그것이 여러분 과제 설계의 출발점입니다.

PART 2 · 오케스트레이션SIX ROLES OF AI
과제를 좁히는 프레임

"AI가 무엇을 한다"가 아니라 "어느 단계에서 어떤 역할을 맡는다"로 설명해야 아이디어가 산출물로 바뀝니다.

역할 ①

생성

보도자료 초안, 안내문, 카드뉴스 문안, 보고서 문장을 만든다.

예: 온실가스 감축 사업 보도자료 초안 생성

역할 ②

변환

형식을 바꾼다. HWP→표준 데이터, 회의 녹취→회의록, 표→문장.

예: 지자체 제출 HWP 양식을 CSV로 구조화

역할 ③

추출

긴 자료에서 필요한 항목만 뽑는다. 조항, 수치, 기한, 담당.

예: 100쪽 환경영향평가서에서 저감 대책만 목록화

역할 ④

분류

기준에 따라 나눈다. 민원 유형, 사업 분야, 위험 등급.

예: 환경 민원을 8개 유형·담당 부서로 자동 분류

역할 ⑤

판단보조

사람의 결정에 근거와 후보를 제시한다. 최종 판단은 사람.

예: 시설 점검 데이터 기반 위험도 우선순위 제안

역할 ⑥

대화

묻고 답한다. 법령 · SOP · 편람 근거를 달아 응답.

예: 환경규제 Q&A 챗봇 (RAG로 조항 출처 표시)

우리 과제의 AI가 생성하는지, 변환하는지, 추출하는지, 분류하는지, 판단을 보조하는지, 대화하는지부터 정하십시오. 하나의 과제에 역할은 1~2개면 충분합니다.
근거: AI 개입 6가지 역할 프레임 · 선발과제 반복 유형(법령·SOP 챗봇, 문서 자동화, 민원 안내, 위험도 예측)에 대응10
과제를 좁히는 가장 빠른 프레임입니다. 우리 AI가 생성하는지, 변환하는지, 추출하는지, 분류하는지, 판단을 보조하는지, 대화하는지 — 이것부터 정하십시오. 하나의 과제에 역할은 한두 개면 충분합니다. 역할이 정해지는 순간 아이디어가 산출물로 바뀝니다. 각 카드 아래 예시는 전부 기후·에너지·환경 실제 업무 장면입니다.

PART 3 · 문제정의PROBLEM DEFINITION FIRST
1시간 중 55분

좋은 AI 과제는 기술 선택 전에 문제를 정확히 듣는 데서 시작합니다.

"1시간이 주어지면 55분은 문제정의에 쓴다"는 오래된 비유가 있습니다. 중요한 것은 출처가 아니라 순서입니다 — 공감, 정의, 그다음 기술.

디자인싱킹의 순서

① 공감 — 현장 담당자·국민·기관의 목소리를 듣는다
② 정의 — 한 명의 페르소나와 한 문장의 문제로 좁힌다
③ 그다음에야 기술 — 블록 조합을 고른다

추상적인 사용자가 아니라, 특정한 한 사람의 불편에서 시작할 때 서비스가 선명해집니다
문제를 듣는 곳이런 신호를 찾으십시오문제 문장 예시
내 업무매주 반복되는 취합 · 매번 틀리는 정리 · 매일 반복되는 검색"매주 월요일 17개 시·도 제출 엑셀을 수작업으로 합치는 데 3시간 쓴다"
동료의 업무옆자리에서 반복적으로 들리는 한숨과 야근 사유"점검 나갈 때마다 과거 지적사항을 찾는 데 30분 걸린다"
현장 · 시설수기 기록, 사진만 쌓이는 자료, 전화로만 도는 정보"현장 점검 메모가 보고서 문장이 되기까지 이틀 걸린다"
국민 · 민원같은 질문의 반복, 안내문을 읽고도 다시 오는 전화"층간소음·악취 민원의 60%가 같은 5개 질문이다"
기관 · 부처제출 양식 불일치, 부서마다 다른 서식, 기한 관리 누락"산하기관 보고 양식이 제각각이라 매번 다시 만든다"

좋은 AI 과제는 멋진 기술명에서 시작하지 않습니다. 반복되는 짜증에서 시작합니다.

근거: 미시 페인포인트와 업무 재설계 · "현장의 작은 병목이 AX의 출발점이다"12
아인슈타인에게 곧잘 연결되는 오래된 비유가 있습니다 — 1시간이 주어지면 55분은 문제정의에 쓴다. 누가 한 말인지보다 순서가 중요합니다. 공감, 정의, 그다음에야 기술입니다. 오른쪽 표의 다섯 줄이 문제를 '듣는 곳'입니다. 내 업무, 동료, 현장, 국민, 기관. 좋은 과제는 멋진 기술명이 아니라 반복되는 짜증에서 시작합니다. 각 팀은 이 표에서 자기 문제 문장을 하나 골라 보십시오.

쓰이지 않는 웹앱

유지보수 안 되는 코드

② 검증되는가결과가 맞는지 확인하는 절차(근거 표시 · 샘플 대조 · 사람 승인)가 있는가
③ 남는가사용법 · 데이터 출처 · 한계가 문서로 남아 있는가
④ 이어받을 수 있는가내가 자리를 옮겨도 다음 담당자가 그대로 운영할 수 있는가
AI 프렌즈의 목표는 "만드는 것"을 넘어 쓰이는 것과 남는 것15

두 가지 되물음

소버린 AI는 모델·인프라만의 문제가 아니고, DX의 성과는 "플랫폼을 만들었다"가 아니라 "업무가 바뀌었다"로 설명되어야 합니다.

결론기후·에너지·환경부의 AI는 기후·에너지·환경 현장을 아는 사람 — 즉 여러분이 만들어야 합니다
되물음 ② DX 시대의 교훈

플랫폼은 많이 만들어졌다. 그런데 쓰였는가

DX 시대에 만든 것수많은 데이터 분석, 정보 플랫폼, 대시보드
다시 물어야 할 것현장 의사결정에 연결됐는가 · 국민 경험을 바꿨는가 · 담당자가 지금도 열어보는가
AI 시대의 성과 문장"AI를 썼다"가 아니라 "업무가 어떻게 줄었고, 판단이 어떻게 빨라졌고, 근거가 어떻게 남았는가"
이번 활동의 성공 보고는 이렇게 쓰여야 합니다 — "주간 취합 3시간이 20분으로 줄었고, 모든 답변에 근거 조항이 남는다."
근거: 공공부문 AI 도입 — PoC/MVP 중심의 작고 빠른 실험 원칙16
두 가지를 되묻겠습니다. 첫째, 소버린 AI는 우리 모델·데이터·인프라만이 아니라 우리 문제를 우리 방식으로 푸는 사고방식까지입니다. 기후·에너지·환경부의 AI는 이 현장을 아는 여러분이 만들어야 합니다. 둘째, DX 시대에 플랫폼과 대시보드는 많이 만들어졌습니다. 다시 물어야 합니다 — 업무가 바뀌었는가. 성공 보고는 아래 문장처럼 쓰여야 합니다. 주간 취합 3시간이 20분으로 줄었고, 모든 답변에 근거 조항이 남는다.
