로컬 코딩 하네스 구현 문서

이 문서는 mini-harness 프로젝트를 기준으로, 사용자가 명령을 입력했을 때 하네스가 내 컴퓨터에서 어떤 코드를 실행하는지 설명합니다.

설명 범위는 CLI 입력 처리, 시스템 프롬프트 생성, LLM 호출, tool_call 파싱, 권한 판단, 사용자 승인, 파일 읽기와 수정, 검색, shell 실행, 세션 로그 저장입니다.

이 문서는 비유를 사용하지 않습니다. 각 구성요소를 소프트웨어 구성요소, 함수 호출, 데이터 구조, 실행 순서로 설명합니다.

목표: opencode류 하네스의 최소 구현을 직접 만들 수 있도록 필요한 파일과 코드를 파악하는 것입니다.

하네스의 정확한 정의

이 문서에서 하네스는 LLM의 텍스트 출력을 로컬 컴퓨터 작업으로 변환하는 런타임을 뜻합니다.

LLM은 파일을 직접 읽거나 수정하지 않습니다. LLM은 정해진 JSON 형식으로 도구 호출 의사를 출력합니다. 하네스는 그 JSON을 검사한 뒤 실제 JavaScript 함수로 연결합니다.

사용자 입력
→ 시스템 프롬프트와 메시지 배열 구성
→ LLM 호출
→ LLM이 final 또는 tool_call JSON 반환
→ 하네스가 JSON 파싱
→ 도구 존재 여부 확인
→ 인자 검증
→ 권한 정책 확인
→ 필요 시 사용자 승인
→ 로컬 도구 실행
→ 실행 결과를 다시 메시지 배열에 추가
→ 반복

따라서 하네스의 구현 핵심은 agent loop, tool registry, permission policy, local executor, session store입니다.

실행 시작점

사용자가 터미널에서 node src/index.js --root example-app "작업 지시"를 실행하면 가장 먼저 src/index.js가 실행됩니다.

index.js는 CLI 인자를 파싱하고, 도구 등록소를 만들고, skill 파일을 읽고, 시스템 프롬프트를 생성하고, 세션 저장소를 초기화하고, LLM 어댑터를 만든 뒤 AgentLoop를 시작합니다.

index.js
→ parseArgs()
→ new ToolRegistry(root)
→ loadSkillPrompt(skill)
→ buildSystemPrompt(...)
→ new JsonlSessionStore(root)
→ createLLM()
→ new AgentLoop(...)
→ loop.run(prompt)

LLM 응답 프로토콜

이 구현은 provider-native tool calling을 사용하지 않고, LLM이 일반 텍스트로 JSON을 반환하도록 설계했습니다. 이유는 하네스의 내부 동작을 코드 수준에서 분명하게 보기 위해서입니다.

LLM은 매 단계에서 둘 중 하나만 반환해야 합니다.

도구 호출

{
  "type": "tool_call",
  "reason": "왜 이 도구가 필요한지",
  "tool": "read_file",
  "args": { "path": "auth.js" }
}

최종 답변

{
  "type": "final",
  "content": "사용자에게 보여줄 결과 요약"
}

하네스는 이 JSON을 parseAction으로 파싱하고, AgentLoop에서 실행 가능한 액션인지 검증합니다.

AgentLoop의 책임

src/agent/loop.js의 AgentLoop 클래스가 하네스의 실행 흐름을 담당합니다.

이 클래스는 사용자 입력을 messages 배열에 추가하고, LLM을 호출하고, LLM 액션을 판별하고, 도구 호출을 처리하고, 결과를 다시 messages 배열에 추가합니다.

중요한 점은 AgentLoop가 직접 파일을 수정하지 않는다는 것입니다. AgentLoop는 도구 등록소에 작업을 위임합니다. 이 분리 때문에 도구 추가, 권한 정책 수정, LLM 교체가 쉬워집니다.

AgentLoop
- messages 상태 관리
- LLM next 호출
- action type 검사
- 도구 존재 여부 검사
- 도구 인자 검증
- 권한 정책 호출
- 승인 요청 호출
- registry.run 호출
- tool result를 LLM 메시지로 재삽입

ToolRegistry의 책임

src/tools/registry.js는 하네스가 사용할 도구를 한 곳에 모읍니다.

각 도구는 이름, 설명, JSON schema, run 함수로 구성됩니다. LLM에게는 설명과 schema를 전달하고, 실제 실행 시에는 같은 registry에서 run 함수를 찾습니다.

이 설계는 LLM에게 보여주는 도구 목록과 실제 실행 가능한 도구 목록을 일치시킵니다. LLM이 존재하지 않는 도구를 호출하면 AgentLoop가 실행하지 않고 오류를 메시지로 되돌립니다.

파일 도구의 책임

src/tools/file-tools.js는 로컬 파일 시스템 접근을 담당합니다. 구현된 도구는 list_files, read_file, write_file, edit_file입니다.

파일 접근은 항상 resolveInsideRoot를 거쳐야 합니다. 이 함수는 요청 경로가 프로젝트 루트 밖으로 나가는지 검사합니다.

edit_file은 전체 파일을 새로 쓰는 방식이 아니라 old_text가 정확히 한 번 존재할 때만 new_text로 바꿉니다. 이 방식은 잘못된 수정 범위를 줄입니다.

검색 도구의 책임

src/tools/search-tools.js는 프로젝트 파일에서 문자열 또는 정규식 검색을 수행합니다.

검색은 LLM이 전체 프로젝트 내용을 한 번에 받지 않고 필요한 파일을 찾기 위한 단계입니다. 검색 결과는 파일 경로, 줄 번호, 해당 줄 텍스트로 구성됩니다.

실제 제품에서는 ripgrep을 우선 사용하고 실패 시 JavaScript 검색으로 대체하는 방식이 자주 사용됩니다. 이 예제도 유사한 구조를 가집니다.

bash 도구의 책임

src/tools/bash-tools.js는 shell 명령을 로컬 컴퓨터에서 실행합니다. 이 도구는 파일 수정 도구보다 더 위험하므로 기본 권한이 ask입니다.

실행은 child_process.spawn으로 이루어집니다. 실행 디렉터리는 프로젝트 루트입니다. stdout과 stderr는 문자열로 누적되고, 종료 코드와 함께 LLM에게 반환됩니다.

timeout이 반드시 필요합니다. 명령이 종료되지 않으면 하네스가 무한히 기다릴 수 있기 때문입니다. 이 예제는 최대 timeout도 제한합니다.

권한 정책의 책임

src/permission/policy.js는 도구 호출을 실행하기 전에 allow, ask, deny 중 하나를 반환합니다.

  • allow: 읽기 전용 작업처럼 즉시 실행 가능한 작업입니다.
  • ask: 파일 수정 또는 shell 실행처럼 사용자 승인이 필요한 작업입니다.
  • deny: 위험 패턴에 해당하여 실행하지 않는 작업입니다.

권한 판단은 한 곳에서 처리해야 합니다. skill, plugin, subagent가 별도 권한 판단을 갖기 시작하면 실행 경로 추적이 어려워집니다.

세션 로그의 책임

src/session/jsonl-store.js는 하네스 실행 기록을 JSON Lines 파일로 저장합니다.

로그에는 사용자 입력, LLM 액션, 권한 판단, 승인 여부, 도구 실행 결과, 최종 답변이 들어갑니다.

디버깅할 때 이 로그가 중요합니다. 잘못된 파일 수정이 발생했을 때 어떤 LLM 액션이 어떤 도구 호출로 연결되었는지 확인할 수 있습니다.

safe-path의 책임

src/utils/safe-path.js는 로컬 하네스에서 반드시 필요한 경로 안전장치입니다.

사용자가 지정한 상대 경로를 프로젝트 루트 기준 절대 경로로 변환한 뒤, 변환된 경로가 프로젝트 루트 내부인지 검사합니다.

예를 들어 ../../.ssh/id_rsa 같은 요청은 프로젝트 루트 밖으로 나가므로 오류를 발생시킵니다.

skill의 위치

src/skills 아래 Markdown 파일은 하네스가 아닙니다. 이 파일은 LLM에게 추가로 전달되는 작업 지침입니다.

하네스의 실행 루프, 권한 정책, 도구 실행은 변하지 않습니다. skill은 시스템 프롬프트에 추가되어 LLM의 도구 선택과 답변 형식에 영향을 줍니다.

이 구조를 사용하면 작업별 지침은 여러 개 둘 수 있지만, 실제 실행 책임은 단일 하네스가 유지합니다.

실제 실행 순서 예시

사용자 명령이 example-app의 로그인 버그를 고쳐줘라고 가정합니다.

  1. CLI가 명령을 받아 loop.run()으로 전달합니다.
  2. AgentLoop가 사용자 입력을 messages 배열에 추가합니다.
  3. LLM이 grep 도구 호출을 반환합니다.
  4. AgentLoop가 registry에 grep 도구가 있는지 확인합니다.
  5. 권한 정책이 read-only 도구로 판단하여 allow를 반환합니다.
  6. registry가 search-tools의 grep 실행 함수를 호출합니다.
  7. 검색 결과가 messages 배열에 TOOL_RESULT로 추가됩니다.
  8. LLM이 read_file을 호출합니다.
  9. 파일 내용이 LLM에게 전달됩니다.
  10. LLM이 edit_file을 호출합니다.
  11. 권한 정책이 ask를 반환하고 사용자의 승인을 요구합니다.
  12. 승인되면 파일이 수정됩니다.
  13. LLM이 run_bash를 호출해 테스트를 실행합니다.
  14. 테스트 결과가 LLM에게 전달됩니다.
  15. LLM이 final 응답을 반환합니다.

직접 만들 때 최소 구현 범위

처음부터 TUI, MCP, LSP, subagent를 만들 필요는 없습니다. 먼저 다음 파일이 있으면 기본 하네스가 작동합니다.

  • index.js: CLI 진입점
  • loop.js: agent loop
  • prompt.js: 시스템 프롬프트와 도구 목록 구성
  • registry.js: 도구 등록 및 실행
  • file-tools.js: 파일 읽기와 수정
  • search-tools.js: 코드 검색
  • bash-tools.js: 테스트와 빌드 실행
  • policy.js: 권한 판단
  • jsonl-store.js: 실행 로그

이 문서의 뒤쪽에는 각 파일을 줄 단위로 설명합니다.

라인별 코드 해설 안내

다음 페이지부터는 프로젝트 파일을 줄 단위로 설명합니다.

각 표는 네 열로 구성됩니다.

  • 줄: 원본 파일의 줄 번호입니다.
  • 코드: 해당 줄의 실제 코드입니다.
  • 설명: 그 줄이 런타임에서 맡는 역할입니다.
  • 분류: import, function, condition, tool, config 같은 범주입니다.

빈 줄과 닫는 중괄호도 표시합니다. 이유는 실제 하네스 코드를 읽을 때 블록 범위를 정확히 따라가야 하기 때문입니다.

이때도 AgentLoop, ToolRegistry, policy.js는 그대로 유지됩니다. 바뀌는 것은 LLM에서 다음 액션을 받아오는 어댑터뿐입니다.

provider-native tool calling으로 바꿀 때

실전 제품에서는 JSON 텍스트 파싱 대신 모델 제공자의 tool calling 기능을 사용할 수 있습니다.

변경 지점은 llm/openai-compatible.js와 agent/prompt.js입니다. 도구 스키마를 provider API의 tools 필드로 전달하고, 응답의 tool_calls 배열을 하네스의 내부 action 형식으로 변환합니다.

{
  type: "tool_call",
  tool: providerToolCall.function.name,
  args: JSON.parse(providerToolCall.function.arguments),
  reason: "provider native tool call"
}

권한 판단과 실제 도구 실행은 계속 AgentLoop에서 수행해야 합니다.

MCP를 추가할 위치

MCP client는 tools/registry.js 근처에 붙이는 것이 적절합니다. MCP 서버에서 제공하는 tools 목록을 읽고, registry에 동적으로 추가합니다.

중요한 점은 MCP 서버가 도구를 제공하더라도 권한 판단은 policy.js를 통과해야 한다는 것입니다.

MCP server tool 목록 수집
→ registry에 mcp.github.create_issue 같은 이름으로 등록
→ LLM에게 tool spec 제공
→ LLM이 tool_call 반환
→ policy.js에서 권한 판단
→ 승인 후 MCP client가 서버로 호출 전달

LSP를 추가할 위치

LSP 기능은 tools/lsp-tools.js로 추가하는 것이 좋습니다. 이 파일은 language server 프로세스를 관리하고, goToDefinition, findReferences, hover 같은 요청을 도구로 제공합니다.

초기에는 read-only 도구로 두는 것이 안전합니다. LSP는 코드 위치와 의미 정보를 주는 기능부터 시작하고, 자동 수정 기능은 별도 검증 후 추가해야 합니다.

subagent를 추가할 위치

초기 하네스에서는 subagent를 만들 필요가 없습니다. 필요해지면 별도 런타임을 만들지 말고, 동일한 AgentLoop 클래스를 다른 systemPrompt, tool allowlist, maxSteps로 실행하는 방식이 적절합니다.

new AgentLoop({
  root,
  llm,
  registry: readOnlyRegistry,
  systemPrompt: reviewerPrompt,
  sessionStore,
  maxSteps: 8
})

이 경우에도 실제 도구 실행과 권한 정책은 한 코드 경로를 유지합니다.

TUI를 추가할 위치

TUI는 하네스 실행 로직 바깥에 두는 것이 좋습니다. AgentLoop는 이벤트를 발생시키고, TUI는 그 이벤트를 화면에 표시합니다.

현재 예제는 console.log를 사용합니다. 실전에서는 다음 이벤트를 구조화해서 UI 레이어로 전달합니다.

  • llm_action
  • permission_request
  • approval_result
  • tool_started
  • tool_result
  • final
  • error

운영 시 필요한 추가 안전장치

  • 민감한 환경변수 마스킹
  • 명령어 allowlist 또는 blocklist 확장
  • git diff 자동 표시
  • 수정 전 파일 snapshot 저장
  • 롤백 명령 제공
  • 대용량 출력 truncation 정책
  • 경로 접근 감사 로그
  • network 접근 제어
  • 프로젝트별 권한 설정 파일

로컬 하네스는 사용자의 권한으로 실행됩니다. 따라서 권한, 로그, 경로 제한, timeout은 선택 기능이 아니라 기본 기능으로 보아야 합니다.

직접 구현할 때 다음 항목을 모두 확인하십시오.

  • LLM 출력이 항상 파싱 가능한 액션 형식인가?
  • 존재하지 않는 도구 호출을 차단하는가?
  • 도구 인자 누락을 실행 전에 잡는가?
  • 파일 접근이 프로젝트 루트 내부로 제한되는가?
  • 파일 수정은 사용자 승인 후 실행되는가?
  • shell 명령은 timeout과 위험 패턴 차단을 갖는가?
  • 도구 결과가 LLM에게 다시 전달되는가?
  • LLM이 실패한 도구 결과를 성공으로 말하지 않도록 프롬프트와 검증 로직을 갖는가?
  • 모든 단계가 세션 로그에 남는가?
  • 최대 step 제한이 있는가?
