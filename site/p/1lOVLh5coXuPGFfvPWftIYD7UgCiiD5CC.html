1 장

웹은 어떻게 굴러가는가

"백엔드"라는 말을 쓰기 전에, 웹사이트 하나가 화면에 뜨기까지 무슨 일이 벌어지는지부터 보겠습니다.

화면은 내 컴퓨터에, 자료는 남의 컴퓨터에

여러분이 지금 인터넷 쇼핑몰에 접속했다고 해봅시다. 상품 사진이 뜨고, 가격이 보이고, 장바구니 버튼이 있습니다. 이 화면은 여러분의 브라우저 안에서 그려집니다. 글자 크기를 바꾸고 버튼에 색을 입히는 일은 전부 여러분 컴퓨터가 합니다.

그런데 가격이 얼마인지는 여러분 컴퓨터가 알 수 없습니다. 어제 만 원이던 것이 오늘 팔천 원일 수 있고, 그 정보는 쇼핑몰 회사가 쥐고 있습니다. 그래서 브라우저는 접속할 때마다 회사의 컴퓨터에 물어봅니다. "이 상품 지금 얼마죠?" 그리고 돌아온 답을 화면에 그립니다.

이 두 세계를 부르는 이름이 있습니다. 브라우저 쪽, 즉 사람 눈에 보이는 쪽을 프론트엔드라고 합니다. 회사 컴퓨터 쪽, 즉 자료를 쥐고 답해주는 쪽을 백엔드라고 합니다. 앞과 뒤라는 뜻입니다. 어려운 말이 아닙니다.

왜 자료를 브라우저에 두면 안 되나

"그냥 가격도 브라우저에 적어두면 안 되나?" 하는 의문이 들 수 있습니다. 실제로 그렇게 만들 수 있고, 그런 것을 정적 웹페이지라고 합니다. 회사 소개 페이지처럼 내용이 거의 안 바뀌면 그걸로 충분합니다.

하지만 방명록을 그렇게 만들면 어떻게 될까요. 제가 글을 남겨도 그 글은 제 브라우저 안에만 있습니다. 여러분이 접속하면 아무것도 안 보입니다. 제가 브라우저를 닫으면 사라집니다. 여러 사람이 함께 보는 것, 시간이 지나도 남아 있는 것. 이 두 가지가 필요한 순간 백엔드가 필요해집니다.

한 문장 정의

백엔드는 여러 사람이 공유하고 오래 남아야 하는 것을 맡아주는 곳입니다. 이 책 전체가 이 한 문장을 풀어 쓴 것입니다. 뒤에 나오는 모든 용어와 명령은 결국 이 일을 하기 위한 도구입니다.

믿을 수 없는 쪽과 믿을 수 있는 쪽

여기서 초보자가 반드시 알아야 할 사실이 하나 있습니다. 프론트엔드는 믿을 수 없습니다.

브라우저에서 도는 코드는 사용자 컴퓨터 안에 있습니다. 사용자가 마음만 먹으면 열어보고 고칠 수 있습니다. "글자는 300자까지"라는 제한을 화면에 걸어두어도, 개발자 도구를 열어 그 제한을 지워버리면 그만입니다. 가격을 만 원에서 백 원으로 바꿔서 보낼 수도 있습니다.

그래서 정말 지켜져야 하는 규칙은 백엔드에 둡니다. 사용자가 손댈 수 없는 곳에서 한 번 더 검사하는 것입니다. 이 원칙 하나가 이 책에서 가장 자주 반복될 이야기입니다.

이 책에서 만들 것

사진 한 장을 붙일 수 있는 방명록을 만듭니다. 닉네임과 한 줄 메시지를 남기고, 원하면 사진을 올립니다. 남긴 글은 목록으로 쌓이고, 다른 사람도 볼 수 있습니다.

소박해 보이지만 백엔드가 하는 일이 전부 들어 있습니다. 글자를 저장하고, 사진이라는 파일을 보관하고, 이상한 입력을 걸러내고, 요청이 오면 답해줍니다.

그리고 이 방명록을 두 번 만듭니다. 2부에서는 Supabase를 백엔드로 삼아 한 번, 3부에서는 Cloudflare를 백엔드로 삼아 다시 한 번. 화면은 거의 똑같이 두고 뒤쪽만 통째로 갈아 끼웁니다.

두 서비스를 합치는 것이 아닙니다

Supabase와 Cloudflare를 연결해서 하나를 만드는 것이 아닙니다. 각각이 그 자체로 완결된 백엔드입니다. 실무에서 둘을 섞어 쓰는 경우도 있지만, 처음 배울 때 그렇게 하면 어느 쪽이 무슨 일을 하는지 영영 구분이 안 됩니다.

같은 요리를 두 개의 부엌에서 만들어 보는 것과 같습니다. 칼과 불이 어디에 있는지가 부엌마다 다를 뿐, 만드는 것은 같은 요리입니다. 두 번째 부엌에 들어갔을 때 비로소 첫 번째 부엌의 구조가 눈에 들어옵니다.

2 장

백엔드를 이루는
세 부품

백엔드는 하나의 물건이 아닙니다. 적어도 세 가지가 모여야 백엔드 노릇을 합니다.

"백엔드를 만든다"는 말이 막연하게 들리는 이유는, 그것이 하나가 아니라 여러 부품의 묶음이기 때문입니다. 방명록에 필요한 것을 하나씩 세어 보겠습니다.

첫째, 데이터베이스 — 글자와 숫자를 담는 곳

남긴 글을 어딘가에 적어두어야 합니다. 그 "어딘가"가 데이터베이스입니다. 엑셀 표를 떠올리면 거의 정확합니다.

엑셀에 시트가 있듯 데이터베이스에는 테이블이 있습니다. 엑셀의 열(세로줄)에 해당하는 것이 컬럼이고, 행(가로줄)에 해당하는 것이 레코드, 즉 한 건의 자료입니다.

엑셀과 다른 점이 두 가지 있습니다. 하나는 규칙을 미리 걸어둘 수 있다는 것입니다. "닉네임은 반드시 있어야 하고 20자를 넘을 수 없다"고 정해두면, 그 조건을 어긴 자료는 들어가지 못하고 거부됩니다. 엑셀은 아무거나 적어도 받아주지만 데이터베이스는 그렇지 않습니다.

다른 하나는 여럿이 동시에 써도 안 깨진다는 것입니다. 같은 순간에 백 명이 글을 남겨도 순서대로 차곡차곡 들어갑니다. 엑셀 파일을 여러 명이 동시에 저장하면 벌어지는 일과 비교하면 큰 차이입니다.

SQL 이라는 말

데이터베이스에게 시키는 말이 SQL입니다. "이 표에서 최근 것 50개 꺼내와" 같은 지시를 정해진 문법으로 적는 것입니다. 이 책에서 SQL을 직접 쓸 일은 없습니다. 에이전트가 씁니다. 다만 나온 결과를 읽을 수는 있어야 하므로, 나올 때마다 무슨 뜻인지 짚겠습니다.

둘째, 파일 저장소 — 사진과 문서를 담는 곳

사진은 데이터베이스에 넣지 않습니다. 넣을 수는 있지만 넣지 않습니다. 데이터베이스는 글자와 숫자를 빠르게 찾는 데 특화된 도구이고, 사진 한 장은 방명록 글 수천 건보다 큽니다. 표 안에 사진을 쑤셔 넣으면 표 전체가 느려집니다.

그래서 사진 같은 파일은 따로 보관합니다. 그 창고를 파일 저장소 또는 오브젝트 스토리지라고 부릅니다. 클라우드에 있는 커다란 사물함이라고 생각하면 됩니다.

동작 방식은 사물함과 비슷합니다. 파일을 넣을 때 이름표(키)를 붙여 넣고, 꺼낼 때 그 이름표를 대면 파일이 나옵니다. 데이터베이스에는 파일 자체가 아니라 이름표만 적어둡니다.

셋째, 서버 코드 — 판단하는 부분

자료를 담을 곳이 생겼다고 끝이 아닙니다. 판단이 필요합니다. 들어온 글이 300자를 넘지 않는지, 닉네임이 비어 있지 않은지, 같은 사람이 1초에 백 번 글을 남기고 있지는 않은지. 이런 판단을 하는 것이 서버 코드입니다.

1장에서 말한 대로 이 판단은 브라우저에 두면 안 됩니다. 사용자가 지울 수 있기 때문입니다. 그래서 사용자가 손댈 수 없는 곳에서 돌아야 하고, 그 자리가 서버입니다.

여기서 두 백엔드가 갈라집니다

이 세 번째 부품을 어떻게 마련하느냐가 Supabase와 Cloudflare의 가장 큰 차이입니다. 미리 한 줄로 말해두면 이렇습니다.

Supabase는 서버 코드를 안 써도 되게 해줍니다. 대신 데이터베이스 자체에 규칙을 걸어둡니다. 규칙이 문지기 노릇을 합니다.

Cloudflare는 서버 코드를 여러분이 씁니다. 대신 데이터베이스가 바깥에 노출되지 않습니다. 코드가 문지기입니다.

지금은 이해가 안 되어도 괜찮습니다. 2부와 3부를 각각 끝내고 4부에서 다시 만나면 그때는 몸으로 알게 됩니다. 지금은 "문지기가 두 종류구나" 정도만 기억하십시오.

3 장

API, 요청과 응답

브라우저가 백엔드에게 말을 거는 방법. 이 장을 이해하면 오류 메시지가 읽히기 시작합니다.

API는 창구입니다

은행에 가면 아무 문이나 열고 들어가 금고를 뒤지지 않습니다. 창구에 가서 정해진 양식으로 요청합니다. "출금이요, 계좌번호는 이것, 금액은 이것." 직원은 조건을 확인하고 돈을 주거나 거절합니다.

API가 바로 그 창구입니다. 백엔드가 "이런 요청은 이렇게 보내주세요"라고 미리 정해둔 통로입니다. 정해진 창구가 아니면 아무리 두드려도 열리지 않습니다. 그래서 안전하고, 그래서 오류가 나면 원인을 찾을 수 있습니다.

메서드는 네다섯 개만 알면 됩니다. GET은 가져오기, POST는 새로 만들기, PUT은 통째로 바꾸기, DELETE는 지우기입니다. 방명록에서는 GET과 POST 두 개만 씁니다.

응답에는 번호가 붙습니다

백엔드는 답을 보낼 때 세 자리 숫자를 함께 붙입니다. 이 숫자가 무슨 일이 있었는지 요약해 줍니다. 문제가 생겼을 때 가장 먼저 봐야 하는 것이 이 번호입니다.

201새로 만들어졌다. POST가 성공했을 때
400보낸 내용이 잘못됐다. 빈 값, 글자 수 초과 등
401신분 확인 실패. 키가 없거나 틀렸다
403신분은 맞는데 권한이 없다. 규칙이 막았다
404그런 창구가 없다. 주소를 잘못 썼다
500·502백엔드 쪽이 터졌다. 내 잘못이 아닐 수도 있다
400과 500의 차이가 진단의 출발점입니다

400번대는 보낸 쪽 잘못, 500번대는 받은 쪽 잘못입니다. 400번대가 뜨면 내가 보낸 내용을 보고, 500번대가 뜨면 백엔드 로그를 봐야 합니다. 이 구분만 알아도 헤맬 시간이 절반으로 줄어듭니다.

JSON — 주고받는 형식

요청과 응답의 내용은 대개 JSON이라는 형식으로 적습니다. 사람도 읽을 수 있고 컴퓨터도 읽을 수 있게 만든 표기법입니다. 중괄호 안에 이름: 값을 쉼표로 늘어놓은 것이 전부입니다.

브라우저가 보내는 것
{
  "nickname": "지민",
  "message": "잘 보고 갑니다"
}
백엔드가 돌려주는 것 (목록 조회)
[
  { "nickname": "하윤", "message": "사진 예쁘네요" },
  { "nickname": "성진", "message": "첫 방문이에요" }
]

대괄호 [ ]는 여러 개를 늘어놓은 목록이고, 중괄호 { }는 한 건의 자료입니다. 개발자 도구의 네트워크 탭에서 보게 될 화면이 정확히 이 모양입니다.

이 장의 결론

백엔드를 만든다는 것은 결국 창구를 여는 일입니다. 어떤 주소로, 어떤 메서드로 오면, 무엇을 확인하고, 무엇을 돌려줄지 정하는 것. 2부와 3부에서 하는 일이 바로 이것입니다.

다만 방식이 다릅니다. Supabase는 창구를 자동으로 만들어 줍니다. 테이블을 만들면 그 순간 그 테이블을 읽고 쓰는 창구가 생깁니다. Cloudflare는 창구를 직접 엽니다. 어떤 주소로 오면 무엇을 할지 코드로 적습니다.

4 장

열쇠
왜 키가 여러 개인가

초보자가 가장 많이 막히는 지점입니다. 이름은 많아 보이지만 갈래는 셋뿐입니다.

백엔드에 접근하려면 신분증이 필요합니다. 그 신분증이 키입니다. 그런데 문서를 보면 키 이름이 여럿 나옵니다. publishable, secret, anon, service_role, 개인 액세스 토큰, API 토큰. 처음 보면 뭘 어디에 써야 할지 알 수 없습니다.

기준은 딱 세 가지입니다. 누가 쓰는가, 어디에 놓이는가, 새어나가면 무슨 일이 생기는가.

① 공개키 — 브라우저에 넣는 열쇠

브라우저에서 도는 코드에 넣는 키입니다. 1장에서 말했듯 브라우저 코드는 누구나 열어볼 수 있으므로, 이 키는 처음부터 공개될 것을 전제로 만들어졌습니다. 소스에 그대로 적어도 되고, 깃허브에 올라가도 사고가 아닙니다.

그럼 아무나 이 키로 데이터를 다 가져가지 않을까요? 바로 그래서 이 키 자체에는 권한이 거의 없습니다. 진짜 방어선은 키가 아니라 백엔드에 걸어둔 규칙입니다. "읽는 것은 허용, 지우는 것은 금지" 같은 규칙이 따로 있고, 그 규칙이 지킵니다.

② 비밀키 — 서버에만 두는 열쇠

서버 코드나 내 컴퓨터에서 도는 스크립트가 쓰는 키입니다. 이 키는 규칙을 통째로 무시합니다. "관리자 열쇠"라고 생각하면 됩니다. 무엇이든 읽고 쓰고 지웁니다.

그래서 이 키가 브라우저나 깃허브에 노출되면 그 자체로 사고입니다. 데이터베이스 전체가 공개된 것과 같습니다. "일단 되게 하려고" 잠깐 프론트에 넣어보는 것도 안 됩니다. 배포하면 기록에 남고, 지워도 남습니다.

③ 관리 토큰 — 사람과 도구가 쓰는 열쇠

앞의 둘이 앱이 데이터를 다루는 열쇠라면, 이것은 계정 자체를 조작하는 열쇠입니다. 프로젝트를 새로 만들거나, 배포를 하거나, 설정을 바꾸는 권한입니다. Supabase의 개인 액세스 토큰과 Cloudflare의 API 토큰이 여기 해당합니다.

중요한 것은 이 열쇠가 앱 코드에 절대 들어가지 않는다는 점입니다. 들어갈 자리도 없습니다. 쓰는 쪽은 CLI 도구와 자동화 시스템입니다.

그리고 한 가지 더. 브라우저 로그인이 가능한 환경이라면 이 토큰은 아예 필요 없습니다. 7장에서 하게 될 wrangler login과 supabase login이 브라우저를 띄워 승인을 받고 알아서 처리하기 때문입니다.

브라우저가 본다면 ①, 서버만 본다면 ②, 사람이나 도구가 계정을 조작한다면 ③. 이 세 문장으로 분류되지 않는 키는 지금 단계에서 필요 없는 키입니다.

관리 토큰을 앱 코드에 넣는 것. 넣고 싶어졌다면 대개 구조를 잘못 잡은 것입니다.

키를 깃허브에 올리는 것. .env는 반드시 .gitignore에 넣습니다. 이미 올렸다면 파일을 지우는 것으로 부족합니다. 키를 폐기하고 재발급해야 합니다.

5 장

배포란 무엇인가

내 컴퓨터에서만 되는 것과 세상 누구나 볼 수 있는 것 사이의 거리.

내 컴퓨터에서 되는 것은 아직 아무것도 아닙니다

코드를 다 짜고 브라우저에서 잘 돌아가는 것을 확인해도, 그것은 내 컴퓨터 안의 일입니다. 친구에게 주소를 보내면 열리지 않습니다. 내 컴퓨터를 끄면 사라집니다.

배포는 내 컴퓨터에 있던 것을 인터넷에 늘 켜져 있는 컴퓨터로 옮겨서, 누구나 주소로 접속할 수 있게 만드는 일입니다. 예전에는 서버를 사거나 빌리고, 운영체제를 깔고, 보안 설정을 하고, 24시간 돌봐야 했습니다. 지금은 명령 한 줄이면 됩니다.

로컬과 원격

이 책에서 계속 나올 짝이 있습니다. 로컬과 원격입니다. 로컬은 내 컴퓨터, 원격은 인터넷 저편의 진짜 서비스를 말합니다.

도구들은 대개 두 곳을 따로 관리합니다. 로컬 데이터베이스에 표를 만들었다고 원격에도 생기는 것이 아닙니다. 로컬에 넣은 비밀값이 원격 배포본에 자동으로 들어가지도 않습니다. 초보자가 "분명히 만들었는데 왜 없지?" 하고 헤매는 원인의 대부분이 이것입니다.

이 책의 습관

이 책에서는 명령을 적을 때 로컬인지 원격인지를 항상 명시합니다. 기본값에 의존하지 않습니다. 도구 버전에 따라 기본값이 바뀌기도 하고, 무엇보다 여러분이 지금 어디를 건드리고 있는지 의식하는 것이 이 실습의 핵심이기 때문입니다.

두 백엔드의 배포가 다릅니다

여기서 미리 알아둘 것이 하나 있습니다. Supabase는 웹페이지를 올려주지 않습니다.

Supabase는 데이터베이스와 파일 저장소, 로그인 기능을 제공하는 백엔드 서비스입니다. 여러분이 만든 index.html을 올려서 주소를 주는 기능은 없습니다. 그래서 2부에서는 화면을 내 컴퓨터에서만 열어 확인하고 끝냅니다. 공개하려면 그 파일을 다른 곳에 올려야 합니다.

반면 Cloudflare는 백엔드와 웹페이지를 한 번에 올려줍니다. 명령 한 줄에 데이터베이스도, 파일 저장소도, 서버 코드도, index.html도 함께 배포되고 주소가 하나 나옵니다. 그래서 3부는 공개 주소를 얻는 것으로 끝납니다.

이것은 우열이 아닙니다

"그럼 Cloudflare가 더 좋은 것 아닌가" 싶겠지만, 그렇게 단순하지 않습니다. Supabase는 대신 로그인·회원가입, 실시간 동기화, 자동 생성 창구처럼 직접 만들면 오래 걸리는 것들을 처음부터 갖추고 있습니다. 무엇을 대신 해주는가가 서로 다를 뿐입니다. 17장에서 이 판단을 정리합니다. 그때까지는 판단을 미뤄두고, 일단 둘 다 만들어 보십시오.

0부를 마치며

여기까지가 용어 정리입니다. 정리하면 다섯 문장입니다.

  • 백엔드는 여럿이 공유하고 오래 남아야 하는 것을 맡는 곳이다.
  • 백엔드는 데이터베이스 · 파일 저장소 · 판단하는 부분으로 이루어진다.
  • 브라우저는 API라는 창구를 통해서만 백엔드에 말을 건다.
  • 키는 공개키 · 비밀키 · 관리 토큰 세 갈래뿐이다.
  • 배포는 로컬에 있던 것을 원격으로 옮기는 일이고, 둘은 따로 관리된다.

이 다섯 문장이 편해졌다면 다음 장으로 넘어가도 좋습니다. 아직 흐릿하다면 그래도 괜찮습니다. 2부에서 손으로 한 번 만들고 나서 이 장을 다시 읽으면 훨씬 선명해집니다. 실습을 먼저 하고 돌아오는 것도 좋은 방법입니다.

6 장

에이전트 · MCP · CLI

이 셋이 뒤섞여서 헷갈립니다. 각각 한 문장으로 정리하면 나머지가 따라옵니다.

손, 리모컨, 조작 패널

코딩 에이전트는 손입니다. ChatGPT 데스크톱앱이나 Antigravity가 여기 해당합니다. 내 의도를 듣고 아래 두 도구를 대신 집어 듭니다. 손 자체는 아무것도 만들지 못합니다. 무엇을 쥐여주느냐가 전부입니다.

MCP는 대화형 리모컨입니다. "테이블 하나 만들어줘"라고 말하면 에이전트가 클릭 없이 처리합니다. 명령어를 외울 필요가 없다는 것이 장점이고, 서비스가 미리 열어둔 기능만 쓸 수 있다는 것이 한계입니다.

CLI는 정식 조작 패널입니다. 터미널에 치는 명령입니다. MCP로 안 되는 일, 특히 실제 배포는 결국 CLI가 합니다. 에이전트가 터미널을 쓸 수 있으므로 이것도 대신 쳐줍니다.

여러분이 할 일과 에이전트가 할 일

경계를 분명히 해두겠습니다. 이 경계가 흐려지면 "내가 코딩을 배워야 하나" 하는 지점에서 멈추게 됩니다. 그럴 필요 없습니다.

왼쪽 칸을 다시 보십시오. 코드를 쓰는 일이 하나도 없습니다. 대신 판단이 전부입니다. 이 키가 여기 있어도 되는가, 이 검증이 서버에 있는가, 지금 나온 결과가 내가 시킨 것과 같은가. 이 판단을 대신해 줄 도구는 아직 없습니다. 그래서 4장의 열쇠 지도가 이 책에서 가장 중요한 장입니다.

코드를 몰라도 되지만, 읽을 줄은 알아야 합니다

에이전트가 만든 코드를 한 줄도 이해하지 못한 채 배포까지 갈 수 있습니다. 실제로 그렇게 되기도 합니다. 다만 그 상태에서는 문제가 생겼을 때 아무것도 할 수 없습니다.

이 책이 코드를 설명하는 이유는 여러분이 코드를 쓰게 하려는 것이 아니라 무엇이 잘못됐는지 짚을 수 있게 하려는 것입니다. 각 실습 뒤에 붙은 "확인 포인트"만 짚을 수 있으면 충분합니다.

서버 코드를 안 써도 되는 백엔드

2장에서 백엔드가 세 부품으로 이루어진다고 했습니다. 데이터베이스, 파일 저장소, 그리고 판단하는 부분. Supabase는 이 셋을 모두 갖추고 있는데, 세 번째를 특이한 방식으로 해결합니다.

보통은 서버 코드를 짜서 "이 요청은 받고 저 요청은 거절한다"고 정합니다. Supabase는 그 대신 데이터베이스 자체에 규칙을 걸어둡니다. 그리고 데이터베이스로 들어가는 창구를 인터넷에 열어둡니다. 브라우저가 그 창구로 직접 말을 걸면, 데이터베이스가 규칙을 보고 스스로 허락하거나 거절합니다.

이 방식의 장점은 명확합니다. 만들 것이 적습니다. 테이블을 하나 만들면 그 순간 그 테이블을 읽고 쓰는 창구가 자동으로 생깁니다. 서버를 짜고, 배포하고, 관리할 필요가 없습니다.

대가도 명확합니다. 규칙을 잘못 걸면 데이터가 그대로 노출됩니다. 데이터베이스가 인터넷에 열려 있기 때문입니다. 그래서 Supabase를 쓸 때 가장 중요한 것이 9장에서 다룰 RLS입니다.

photo_path사진 이름표없어도 됨. 10장에서 씀
created_at작성 시각자동으로 지금 시각이 들어감
① 시키는 말
Supabase MCP로 guestbook 프로젝트에 방명록용 테이블을 만들어줘.
- 테이블명 guestbook
- 컬럼: id(자동 증가 기본키), nickname(1~20자 제한),
  message(1~300자 제한), photo_path(비워둘 수 있는 텍스트),
  created_at(생성 시각 자동)
- created_at 내림차순 인덱스

보안은 이렇게 해줘. 이게 제일 중요해.
- RLS를 켤 것
- 읽기(select)는 anon 과 authenticated 모두에게 허용
- 쓰기(insert)도 anon 에게 허용하되, with check 로
  닉네임 1~20자, 메시지 1~300자 조건을 반드시 걸 것
- 수정(update)과 삭제(delete) 정책은 만들지 말 것

마이그레이션으로 남기고 적용한 SQL 전문을 보여줘.
MCP가 읽기 전용이면 실행하지 말고 먼저 알려줘.

② 나온 결과가 아래와 같은지 대조합니다. 줄마다 이해할 필요는 없습니다. 표시해 둔 곳만 짚으면 됩니다.

에이전트가 만들 결과 — 표
create table public.guestbook (
  id          bigint generated always as identity primary key,
  nickname    text not null
              check (char_length(nickname) between 1 and 20),
  message     text not null
              check (char_length(message) between 1 and 300),
  photo_path  text,
  created_at  timestamptz not null default now()
);

create index guestbook_created_idx
  on public.guestbook (created_at desc);

not null은 "비어 있으면 안 된다", check는 "이 조건을 만족해야 한다", default now()는 "안 적어주면 지금 시각을 넣는다"는 뜻입니다. index는 목록을 최신순으로 빨리 꺼내기 위한 색인입니다. 전화번호부의 가나다 순 정렬과 같은 역할입니다.

문지기 세우기 — RLS

여기가 이 장의 본론입니다. RLS는 Row Level Security, 우리말로 행 단위 보안입니다. "이 키를 든 사람이 이 줄을 봐도 되는가"를 데이터베이스가 직접 판단하게 하는 장치입니다.

중요한 것은 켜는 순간 기본값이 전부 금지가 된다는 점입니다. 그리고 허용하고 싶은 것만 정책이라는 이름으로 하나씩 엽니다. 잠긴 문에 열쇠 구멍을 필요한 만큼만 뚫는 것과 같습니다.

에이전트가 만들 결과 — 규칙 (여기를 보십시오)
-- ① 잠금장치를 켠다. 이 줄이 없으면 표 전체가 무방비다.
alter table public.guestbook enable row level security;

-- ② 읽기는 누구에게나 연다.
create policy "누구나 읽기"
  on public.guestbook for select
  to anon, authenticated
  using (true);

-- ③ 쓰기도 열되, 조건을 붙인다. 이 조건이 서버 코드 대신이다.
create policy "조건에 맞으면 쓰기"
  on public.guestbook for insert
  to anon, authenticated
  with check (
    char_length(nickname) between 1 and 20
    and char_length(message) between 1 and 300
  );

-- ④ update, delete 정책은 만들지 않는다.
--    → 아무도 남의 글을 고치거나 지울 수 없다.
확인 포인트 세 개

첫째, enable row level security 줄이 있는가. 이 줄이 없으면 나머지는 아무 의미가 없습니다.

둘째, for select와 for insert 정책이 각각 하나씩 있는가. 읽기 정책이 없으면 목록이 영원히 비어 보이고, 쓰기 정책이 없으면 글이 안 써집니다.

셋째, for update와 for delete 정책이 없는가. 에이전트는 친절하게 전부 만들어 주는 경우가 많습니다. 그러면 아무나 남의 글을 고치고 지울 수 있게 됩니다. 있으면 지워달라고 하십시오.

using 과 with check 의 차이

둘 다 조건을 적는 자리인데 쓰이는 때가 다릅니다. using은 이미 있는 줄을 볼 수 있는지 판단할 때, with check는 새로 들어오는 줄이 조건에 맞는지 판단할 때 씁니다. 그래서 읽기 정책에는 using이, 쓰기 정책에는 with check가 붙습니다.

여기서 무슨 일이 벌어졌나

잠깐 멈춰서 방금 한 일의 의미를 짚겠습니다. with check에 적은 글자 수 조건이 서버 코드가 할 일을 대신하고 있습니다.

보통이라면 서버 코드에 "닉네임이 20자를 넘으면 거절"이라고 적었을 것입니다. 지금은 그 판단이 데이터베이스 안에 들어가 있습니다. 브라우저에서 아무리 조작해서 500자짜리 메시지를 보내도 데이터베이스가 스스로 거절합니다. 서버 코드가 한 줄도 없는데 말입니다.

이것이 8장에서 말한 "규칙이 문지기"라는 말의 실체입니다. 3부에서 같은 일을 코드로 하게 되면 차이가 선명해질 것입니다.

③ 확인 질문
방금 적용한 결과를 네가 직접 확인하고 보고해줘.
1) guestbook 테이블의 RLS 활성화 여부
2) 이 테이블에 걸린 정책을 전부 나열하고, 각각 무엇을 허용하는지
3) 보안 어드바이저를 실행해 경고가 있는지 확인하고,
   각 경고가 무슨 뜻이고 지금 구조에서 문제인지 아닌지 설명
4) 다음 세 가지가 각각 가능한지 근거와 함께 답해줘
   - 공개키로 목록을 읽는 것
   - 공개키로 21자짜리 닉네임을 넣는 것

4번의 답은 순서대로 가능 / 불가능 / 불가능이어야 합니다. 다르게 나왔다면 정책이 잘못 만들어진 것입니다. 이렇게 예상 답을 미리 알고 묻는 것이 에이전트를 쓰는 사람이 가져야 할 가장 실용적인 습관입니다.

10 장

사진 저장소

글자는 표에, 사진은 창고에. 2장에서 말한 두 번째 부품을 만듭니다.

버킷이라는 말

Supabase에서 파일 창고 하나를 버킷이라고 부릅니다. 양동이라는 뜻인데, 그냥 폴더라고 생각해도 무방합니다. 버킷을 만들 때 결정할 것이 하나 있습니다. 공개 버킷이냐 비공개 버킷이냐.

구분읽기쓰기
공개 버킷주소를 아는 사람은 누구나 볼 수 있다규칙이 적용된다
비공개 버킷규칙이 적용된다. 서명된 임시 주소가 필요하다규칙이 적용된다

방명록 사진은 어차피 모두에게 보여줄 것이므로 공개 버킷으로 만듭니다. 공개 버킷은 읽기가 이미 열려 있어서 읽기 정책을 따로 만들 필요가 없습니다. 반면 올리는 것은 공개 버킷에서도 규칙이 적용되므로, 업로드 정책은 만들어야 합니다.

① 시키는 말
Supabase MCP로 사진 저장소를 준비해줘.
1) photos 라는 이름의 공개 버킷을 만들어줘.
   허용 형식은 이미지만, 파일 하나당 최대 5MB.
2) 공개 버킷이니 읽기 정책은 만들지 마.
3) 업로드는 익명 사용자에게도 허용해야 하니
   storage.objects 에 photos 버킷 한정 insert 정책을 만들어줘.
4) update, delete 정책은 만들지 마.
적용한 SQL을 전부 보여주고, 왜 읽기 정책이 필요 없는지도 설명해줘.
에이전트가 만들 결과 — 버킷과 업로드 정책
-- 공개 버킷 만들기
insert into storage.buckets (id, name, public)
values ('photos', 'photos', true);

-- 업로드만 연다. photos 버킷에만.
create policy "photos 업로드 허용"
  on storage.objects for insert
  to anon, authenticated
  with check (bucket_id = 'photos');
확인 포인트

public이 true인가. 이것이 false면 사진이 화면에 안 뜹니다.

업로드 정책에 bucket_id = 'photos' 조건이 있는가. 이 조건이 빠지면 모든 버킷에 업로드가 허용됩니다. 지금은 버킷이 하나뿐이라 티가 안 나지만, 나중에 비공개 버킷을 하나 만드는 순간 구멍이 됩니다.

대시보드 Storage 화면에서 버킷을 만들어도 결과는 같습니다. New Bucket을 누르고 이름을 photos로, Public 스위치를 켜면 됩니다.

사진은 어떻게 오가는가

흐름을 그림으로 정리하면 이렇습니다. 이 순서를 알아두면 11장 코드가 쉽게 읽힙니다.

1
사용자가 사진을 고른다.
2
브라우저가 겹치지 않는 이름을 지어 버킷에 올린다. (예: 1757···-a3f9.jpg)
3
올리기에 성공하면 그 이름표만 방명록 표의 photo_path에 적는다.
4
목록을 보여줄 때는 이름표로 공개 주소를 만들어 <img>에 넣는다.

2번에서 이름을 새로 짓는 이유가 있습니다. 사용자가 올린 파일 이름을 그대로 쓰면 두 사람이 똑같이 photo.jpg를 올렸을 때 나중 것이 앞의 것을 덮어씁니다. 그래서 시각과 임의의 문자를 섞어 겹치지 않는 이름을 만듭니다.

무료 플랜의 사진 관련 한도

전체 저장 용량 1 GB, 파일 하나당 최대 50 MB입니다. 우리는 버킷을 만들 때 5 MB로 더 낮춰 잡았습니다. 방명록 사진에는 충분합니다. 참고로 이미지 자동 리사이즈 기능은 무료 플랜에서 쓸 수 없습니다. 큰 사진을 그대로 보여주게 되니, 실제 서비스라면 올리기 전에 브라우저에서 줄이는 처리가 필요합니다.

화면 붙이기

작업 폴더 정하기

바탕화면 등에 guestbook 폴더를 만들고, 그 안에 supabase-ver 폴더를 만듭니다. 3부에서 만들 Cloudflare 버전과 섞이지 않게 하기 위해서입니다. 이번 장에서 만들 파일은 guestbook/supabase-ver/index.html 하나뿐입니다.

① 시키는 말
guestbook/supabase-ver/index.html 파일을 만들어줘. 조건:

<script>

const SUPABASE_URL     = "https://xxxxx.supabase.co";
const PUBLISHABLE_KEY  = "sb_publishable_...";

// 전역 이름 supabase 를 덮어쓰지 않도록 db 에 담는다
const db = supabase.createClient(SUPABASE_URL, PUBLISHABLE_KEY);

async function load() {
  const { data, error } = await db
    .from("guestbook")
    .select("nickname, message, photo_path, created_at")
    .order("created_at", { ascending: false })
    .limit(50);

  if (error) { list.innerHTML = "<li>불러오지 못했습니다</li>"; return; }

  list.innerHTML = data.map(r => {
    // 이름표로 공개 주소를 만든다. await 도 error 도 없다.
    const img = r.photo_path
      ? `<img src="${db.storage.from("photos")
                      .getPublicUrl(r.photo_path).data.publicUrl}">`
      : "";
    return `<li><b>${esc(r.nickname)}</b>
      <div>${esc(r.message)}</div>${img}</li>`;
  }).join("");
}

첫째, 키가 하나뿐인가. 파일 전체를 secret으로 검색해 아무것도 안 나와야 합니다.

화면 열어보기 — 그냥 더블클릭하면 안 됩니다

python3 -m http.server 8000

동작 확인

  • 글을 하나 남긴다 → 목록에 즉시 뜬다
  • 사진을 붙여 남긴다 → 목록에 사진이 함께 뜬다
  • 닉네임을 21자로 넣어본다 → 실패해야 정상이다
  • 메시지 칸에 <script>alert(1)</script>를 넣는다 → 실행되지 않고 글자로 보여야 한다

세 번째와 네 번째가 이 실습의 진짜 확인 항목입니다. 성공하는 것보다 실패해야 할 것이 실패하는지가 중요합니다.

여기서 Supabase의 한계를 만납니다

잘 동작하는 방명록이 생겼습니다. 그런데 이 주소는 localhost입니다. 친구에게 보내도 열리지 않고, 내 컴퓨터를 끄면 사라집니다.

그럼 이 index.html을 Supabase에 올리면 되지 않을까요. 안 됩니다. Supabase는 웹페이지를 올려주는 기능을 제공하지 않습니다. 파일 저장소에 HTML을 올려도 웹페이지로 뜨지 않고 글자 그대로 보입니다. 보안상 일부러 그렇게 되어 있습니다.

즉 Supabase로 만든 백엔드는 완성됐지만, 화면을 세상에 내놓으려면 다른 곳이 필요합니다. Vercel, Netlify, GitHub Pages, 그리고 다음 장에서 만날 Cloudflare 같은 곳입니다. 이것이 백엔드 서비스와 풀스택 플랫폼의 차이이고, 3부에서 바로 그 차이를 몸으로 겪게 됩니다.

2부를 마치며

백엔드 하나를 완성했습니다. 정리하면 이렇습니다.

표를 만들고, 표 앞에 규칙을 세우고, 사진 창고를 열고, 브라우저가 공개키를 들고 직접 말을 걸게 했습니다. 서버 코드는 한 줄도 쓰지 않았습니다. 그런데도 21자짜리 닉네임은 거부되고, 남의 글은 지울 수 없습니다.

3부에서는 같은 방명록을 전혀 다른 방식으로 만듭니다. 거기서는 서버 코드를 씁니다. 그리고 데이터베이스는 인터넷에서 보이지 않습니다. 다 만들고 나면 두 방식이 각각 무엇을 대신해 주었는지 선명하게 보일 것입니다.

12 장

Cloudflare가
맡아주는 것

3부가 시작됩니다. 두 번째 부엌입니다. 같은 요리를 다른 도구로 만듭니다.

서버 코드를 내가 쓰는 백엔드

Supabase는 데이터베이스를 인터넷에 열어두고 규칙으로 지켰습니다. Cloudflare는 정반대입니다. 데이터베이스가 인터넷에서 아예 보이지 않습니다. 주소도 없고 접속할 방법도 없습니다.

대신 Worker라는 작은 서버 코드가 앞에 섭니다. 브라우저는 Worker에게만 말을 걸 수 있고, Worker만이 데이터베이스와 파일 저장소에 손을 댈 수 있습니다. 무엇을 허용할지는 내가 코드로 적습니다.

바인딩이라는 개념

여기서 처음 보는 말이 나옵니다. 바인딩입니다. Worker가 데이터베이스나 저장소를 쓸 수 있게 미리 묶어두는 것을 말합니다.

중요한 점은 이렇습니다. 바인딩으로 묶으면 Worker 코드 안에서 env.DB, env.PHOTOS 같은 이름으로 바로 씁니다. 주소도 키도 필요 없습니다. Cloudflare가 "이 Worker는 이 데이터베이스를 쓸 자격이 있다"는 것을 이미 알고 있기 때문입니다.

4장 표에서 Cloudflare의 공개키 칸이 "없음"이었던 이유가 이것입니다. 브라우저가 데이터베이스에 직접 접근하지 않으니 브라우저에 넣을 키가 없고, Worker는 바인딩으로 연결되니 코드에 적을 키도 없습니다. 이 방식에서는 키를 다룰 일 자체가 크게 줄어듭니다.

Cloudflare가 제공하는 것

R2파일 저장소14장에서 사용

눈여겨볼 것은 네 번째 줄입니다. Cloudflare는 웹페이지도 함께 올려줍니다. 11장에서 Supabase에는 없다고 확인한 바로 그 기능입니다. 그래서 3부는 명령 한 줄로 백엔드와 화면이 동시에 배포되며 끝납니다.

2부와 무엇이 다를지 미리 봐두기

3부를 시작하기 전에 앞으로 겪을 차이를 한 번 짚어두면 길을 잃지 않습니다.

키를 적지 않습니다. 2부에서는 URL과 공개키를 코드에 적었습니다. 3부에서는 이름만 적고 연결은 Cloudflare가 합니다.

검증을 직접 씁니다. 2부에서는 규칙에 조건을 적었습니다. 3부에서는 코드에 if 문으로 씁니다.

작업 폴더와 프로젝트 만들기

D1 만들기

D1은 Cloudflare가 제공하는 SQL 데이터베이스입니다. Supabase의 Postgres와 문법이 조금 다르지만 개념은 같습니다. 표가 있고 컬럼이 있고 SQL로 다룹니다.

터미널 — 데이터베이스 만들기

실행하면 붙여넣을 설정 조각이 출력됩니다. 그 안에 database_id라는 긴 문자열이 들어 있습니다. 이 값을 wrangler.jsonc에 옮겨 적어야 합니다.

wrangler.jsonc — D1 바인딩 추가
{

  "main": "src/index.js",
  "compatibility_date": "2026-09-06",
  "observability": { "enabled": true },

    {

      "database_name": "guestbook-db",
      "database_id": "위 명령이 알려준 긴 문자열"

표 만들기

SQL 파일을 하나 만들고, 그 파일을 데이터베이스에 흘려넣습니다.

schema.sql
create table if not exists guestbook (
  id          integer primary key autoincrement,
  nickname    text not null,
  message     text not null,
  photo_key   text,
  created_at  text not null default (datetime('now'))
);

create index if not exists guestbook_created_idx
  on guestbook (created_at desc);

9장의 Postgres 문법과 조금 다릅니다. bigint generated always as identity가 integer primary key autoincrement가 되고, timestamptz가 text가 되었습니다. D1의 바탕이 SQLite라는 다른 데이터베이스이기 때문입니다. 이런 차이는 에이전트가 알아서 맞춰줍니다. 여러분이 외울 필요는 없습니다.

글자 수 제한이 사라진 것을 눈치채셨습니까

9장에서는 check (char_length(nickname) between 1 and 20)이 있었습니다. 여기에는 없습니다. 넣을 수도 있지만 일부러 넣지 않았습니다.

이번에는 그 판단을 15장의 Worker 코드가 맡을 것이기 때문입니다. 같은 일을 데이터베이스가 하느냐 코드가 하느냐 — 이것이 두 방식의 갈림길입니다. 16장에서 이 대비를 정리합니다.

로컬과 원격, 두 번 넣습니다

5장에서 말한 로컬과 원격이 여기서 처음 실전으로 나옵니다. D1은 내 컴퓨터 안의 연습용과 인터넷의 진짜가 완전히 따로입니다. 한쪽에 표를 만들어도 다른 쪽에는 생기지 않습니다.

터미널 — 반드시 두 번 실행한다
# ① 내 컴퓨터의 연습용 DB에 (wrangler dev 가 쓰는 쪽)
npx wrangler d1 execute guestbook-db --local --file=./schema.sql

# ② 인터넷의 진짜 DB에 (배포된 Worker 가 쓰는 쪽)
npx wrangler d1 execute guestbook-db --remote --file=./schema.sql

# 확인
npx wrangler d1 execute guestbook-db --local \
  --command="select name from sqlite_master where type='table'"
여기가 초보자가 가장 많이 헤매는 지점입니다

증상은 이렇습니다. 로컬에서는 잘 되는데 배포하면 "테이블이 없다"는 오류가 납니다. 또는 그 반대입니다. 원인은 거의 항상 한쪽에만 표를 만든 것입니다.

그래서 이 책은 --local과 --remote를 모든 명령에 빠짐없이 적습니다. 둘 중 하나를 생략하면 도구가 기본값을 골라주는데, 그 기본값이 무엇인지 문서마다 다르게 적혀 있을 정도로 헷갈립니다. 플래그를 항상 적으면 이 혼란 자체가 사라집니다.

③ 확인 질문
지금 상태를 확인해줘.
1) wrangler.jsonc 의 d1_databases 설정을 보여주고,
   database_id 가 실제 값으로 채워져 있는지
2) --local 과 --remote 양쪽에서 guestbook 테이블이 존재하는지
   각각 확인해서 알려줘
3) 한쪽에만 있다면 없는 쪽에 만드는 명령을 알려줘
명령을 실행할 때는 --local / --remote 를 반드시 명시해줘.

Worker와 배포

문지기를 코드로 세우고, 화면까지 얹어 명령 한 줄로 세상에 내보냅니다.

Worker가 할 일 네 가지

요청하는 일
GET /api/entriesD1에서 최신 50건을 꺼내 JSON으로 돌려준다
POST /api/entries내용을 검사하고 통과하면 D1에 한 줄 넣는다
POST /api/photo사진을 R2에 넣고 이름표를 돌려준다
GET /photo/…R2에서 사진을 꺼내 돌려준다
그 밖의 모든 요청public/ 폴더의 파일을 그대로 내보낸다
① 시키는 말
src/index.js 에 Worker 코드를 써줘.
경로별로 이렇게 처리해줘.

- GET  /api/entries : env.DB 에서 guestbook 최신 50건을 select 해서 JSON 반환
- POST /api/entries : JSON 본문에서 nickname, message, photo_key 를 받아
    * 서버에서 다시 검증: nickname 1~20자, message 1~300자
    * 조건에 안 맞으면 400 과 이유를 반환
    * 통과하면 env.DB 에 insert 하고 201 반환
- POST /api/photo : 요청 본문을 env.PHOTOS 에 저장.
    * 겹치지 않는 키를 서버에서 만들 것
    * Content-Type 을 httpMetadata 로 함께 저장
    * 5MB 를 넘으면 413 반환
    * 성공하면 { key } 를 JSON 으로 반환
- GET  /photo/<키> : env.PHOTOS 에서 꺼내 반환.
    * 없으면 404
    * writeHttpMetadata 로 원래 Content-Type 을 붙일 것
- 그 밖의 요청 : env.ASSETS.fetch(request) 로 넘김

실패 시 상세 오류는 console.error 로만 남기고
사용자에게는 일반적인 메시지만 반환해줘.
D1 은 prepare().bind().run() 형태로 쓰고,
읽기 결과는 results 에서 꺼내줘.

② 나온 결과를 세 조각으로 나눠 보겠습니다.

src/index.js — 입구
export default {
  async fetch(request, env) {
    const url = new URL(request.url);
    const p   = url.pathname;

    if (p === "/api/entries" && request.method === "GET")
      return listEntries(env);
    if (p === "/api/entries" && request.method === "POST")
      return addEntry(request, env);
    if (p === "/api/photo" && request.method === "POST")
      return putPhoto(request, env);
    if (p.startsWith("/photo/") && request.method === "GET")
      return getPhoto(p.slice("/photo/".length), env);

  const photoKey = body.photo_key ?? null;

    return json({ error: "닉네임은 1~20자입니다" }, 400);

  try {
    await env.DB
      .prepare("insert into guestbook (nickname, message, photo_key) values (?, ?, ?)")
      .bind(nickname, message, photoKey)
      .run();
  } catch (e) {

    return json({ error: "저장에 실패했습니다" }, 500);
  }

async function putPhoto(request, env) {
  const type = request.headers.get("content-type") ?? "application/octet-stream";
  const buf  = await request.arrayBuffer();

  if (buf.byteLength > 5 * 1024 * 1024)
    return json({ error: "사진은 5MB 이하만 됩니다" }, 413);

  // 키는 서버가 만든다. 브라우저가 정하게 두면 남의 파일을 덮어쓸 수 있다.
  const ext = type.split("/")[1]?.replace(/[^a-z0-9]/g, "") || "bin";
  const key = `${Date.now()}-${crypto.randomUUID().slice(0, 8)}.${ext}`;

  await env.PHOTOS.put(key, buf, { httpMetadata: { contentType: type } });
  return json({ key }, 201);
}

async function getPhoto(key, env) {
  const object = await env.PHOTOS.get(key);
  if (object === null) return new Response("Not found", { status: 404 });

  const headers = new Headers();
  object.writeHttpMetadata(headers);          // 저장할 때의 형식을 되살린다
  headers.set("etag", object.httpEtag);
  return new Response(object.body, { headers });
}

무엇을 언제 고를까

둘 다 만들어 봤으니 이제 판단할 수 있습니다. 정답은 없지만 기준은 있습니다.

Supabase가 유리한 경우

  • 회원가입과 로그인이 필요할 때. 직접 만들면 가장 오래 걸리고 가장 위험한 부분입니다. 그것이 처음부터 들어 있습니다.
  • 데이터 구조가 복잡할 때. Postgres는 관계형 데이터베이스의 표준에 가깝습니다. 표를 여러 개 연결하고 복잡하게 질의해야 한다면 유리합니다.
  • 여러 사람이 같은 화면을 동시에 볼 때. 실시간 동기화가 내장되어 있습니다.
  • 백엔드만 필요할 때. 화면은 이미 다른 곳에 있고 저장소만 붙이면 되는 경우입니다.
  • 일단 빨리 만들어 보고 싶을 때. 서버 코드 없이 동작하는 것을 만드는 속도는 확실히 빠릅니다.

Cloudflare가 유리한 경우

  • 화면과 백엔드를 한 번에 올리고 싶을 때. 명령 하나로 끝납니다.
  • 요청 처리에 나만의 규칙이 많을 때. 코드로 쓰는 것이 규칙 설정보다 자유롭습니다.
  • 파일을 많이 내보낼 때. R2는 내려받기가 무료입니다. 이미지·영상이 많은 서비스에서 큰 차이가 납니다.
  • 전 세계 사용자를 상대할 때. 코드가 사용자와 가까운 곳에서 실행됩니다.
  • 데이터베이스를 인터넷에 노출하고 싶지 않을 때. 보안 감사나 사내 규정이 있는 경우입니다.
두 가지 흔한 오해

"코드를 안 써도 되니까 Supabase가 초보자용" — 절반만 맞습니다. 코드를 안 쓰는 대신 규칙을 정확히 이해해야 합니다. RLS를 대충 걸어놓은 서비스가 실제로 데이터를 통째로 유출한 사례가 여럿 있습니다. 코드를 안 쓴다는 것이 신경을 안 써도 된다는 뜻은 아닙니다.

"둘 중 하나만 골라야 한다" — 그렇지 않습니다. 실무에서는 섞어 쓰기도 합니다. 다만 둘 다 따로 이해한 다음에 섞어야 합니다. 이해하기 전에 섞으면 문제가 생겼을 때 어느 쪽 문제인지 영원히 모릅니다. 이 책이 두 서비스를 끝까지 분리해서 다룬 이유입니다.

입력칸에 <script>로 시작하는 문자열을 넣어 보는 것은 장난이 아니라 가장 기본적인 보안 점검입니다. 그 글자가 화면에 그대로 보이면 통과, 아무것도 안 보이거나 이상한 일이 생기면 실패입니다.

실패했다면 이스케이프 처리가 빠진 것입니다. 에이전트에게 "사용자 입력을 화면에 그릴 때 이스케이프가 되는지 확인하고 고쳐줘"라고 하면 됩니다. 무엇이 잘못됐는지 말할 수 있으면 고치는 것은 어렵지 않습니다.

결과를 바꾸는 네 가지 습관

금지 조건을 먼저 씁니다. "비밀키는 절대 프론트에 넣지 마"라는 한 문장이 있고 없고의 차이가 큽니다. 하지 말아야 할 것을 말해두지 않으면 에이전트는 가장 빨리 동작하는 길을 고릅니다.

확인 방법까지 지시합니다. "만든 뒤 확인하고 결과를 보여줘"를 붙이면 실제로는 되지 않았는데 완료했다고 보고하는 일이 크게 줄어듭니다.

모르면 모른다고 하라고 명시합니다. "확인되지 않은 것은 추측하지 말고 확인 불가라고 적어줘"라는 문장 하나가 잘못된 정보를 걸러냅니다.

예상 답을 미리 정해두고 묻습니다. "21자 닉네임이 거부되는지 확인해줘"처럼 답이 정해진 질문을 하면, 틀렸을 때 바로 드러납니다.
