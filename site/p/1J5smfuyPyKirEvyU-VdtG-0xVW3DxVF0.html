이 교재는 바이브코딩과 RAG를 경험한 전문인재를 대상으로 합니다. 오전에는 PowerShell, Python, Node.js, 브라우저와 확장 프로그램을 이용해 자료를 수집하고 가공하는 원리와 연결 구조를 살펴봅니다. 오후에는 Context Injection을 중심으로 정적 맥락, 파일 맥락, 구조화 검색, 키워드 검색, 벡터 검색, 하이브리드 검색, 동적 맥락, MCP 도구 연결을 차례로 다룹니다.

RAG는 임베딩과 벡터 데이터베이스만을 뜻하지 않습니다. 질문에 필요한 외부 근거를 찾아 언어모델의 입력으로 구성하는 전체 절차가 중요합니다. 강의 뒤 하루 프로젝트에서는 각자 보유한 문서나 데이터베이스를 맥락으로 활용해 기관과 기관장에게 쓸모 있는 문서검색 AI를 설계합니다.

PART 1

바이브코딩의 재발견

바이브코딩은 웹앱 하나를 만드는 기술이 아닙니다. 반복되는 파일 작업을 PowerShell로 줄이고, 익숙한 엑셀 업무를 VBA로 연결하며, Python으로 문서를 읽고, HTML로 결과를 보여주고, 브라우저와 확장 프로그램을 새로운 업무 화면으로 바꾸는 과정 전체를 포함합니다.

1부에서는 도구의 문법보다 각 도구가 업무 흐름의 어느 지점을 맡는지 살펴봅니다. 자료를 조사하는 일, 형식을 바꾸는 일, 사람이 확인하는 일, 검색 결과를 보여주는 일을 분리하면 코딩 에이전트에게 더 정확하게 일을 맡길 수 있습니다.

1장 전문인재 보수교육에서 다시 바이브코딩을 다루는 이유

이미 경험한 기술을 하나의 업무 흐름으로 연결한다

이 과정의 교육생은 AI챔피언 전문인재 과정을 통해 머신러닝과 생성형 AI를 접했고, 바이브코딩으로 HTML이나 간단한 프로그램을 만들어 본 경험이 있습니다. 따라서 코드 편집기의 기본 조작이나 프롬프트 작성법을 처음부터 길게 설명하지 않습니다. 대신 서로 다른 기술을 기관의 자료 업무 안에서 어떻게 연결할지에 초점을 둡니다.

실무 프로젝트는 화면 하나를 만드는 것으로 끝나지 않습니다. 자료가 있는 폴더를 확인하고, 원본과 출처를 기록하고, 파일에서 텍스트를 읽고, 필요한 값을 구조화하고, 검색 화면에 보여주는 과정이 이어집니다. 공개 뉴스와 회의자료를 정기적으로 가져오려면 API와 예약 실행이 필요할 수 있습니다. 여러 사람이 같은 자료를 사용한다면 데이터베이스와 권한도 설계해야 합니다.

이번 보수교육의 초반부에서는 이 흐름을 PowerShell, Python, Node.js, HTML, 크롬 확장 프로그램, Supabase와 Cloudflare라는 서로 다른 구현 방식으로 펼쳐 봅니다. 각 기술을 깊게 배우는 시간이 아니라, 어떤 업무 단계에 어떤 기술이 적합한지 비교하는 시간입니다.

후반부에서는 이 모든 구현을 하나로 묶는 개념인 Context Injection을 다룹니다. 기관의 문서와 데이터가 언어모델의 입력으로 들어가기 전까지 어떤 선택과 가공이 필요한지를 방식별로 분해합니다. 마지막에는 교육생이 자신의 기관 자료를 선택해 하루 프로젝트의 주제로 바꿉니다.

이번 과정에서 만드는 판단 기준

프로그램이 실행됐다는 사실과 기관 업무에 쓸모가 있다는 평가는 다릅니다. 이 과정에서는 자료의 출처가 남는지, 원본을 다시 열 수 있는지, 기준일이 유지되는지, 외부 서비스로 전송되는 범위가 무엇인지 확인합니다. 인공지능의 답변이 그럴듯한지보다 근거를 다시 확인할 수 있는지를 먼저 평가합니다.

2장 모델, 코딩 에이전트, API, 업무 프로그램을 구분한다

같은 AI라는 이름 아래 서로 다른 역할이 있다

언어모델은 입력된 텍스트를 바탕으로 답변을 생성합니다. 코딩 에이전트는 언어모델의 제안을 이용해 파일을 읽고 수정하며 명령을 실행하는 작업 환경입니다. API는 프로그램이 모델이나 외부 서비스에 정해진 형식으로 요청을 보내는 접점입니다. 업무 프로그램은 사용자의 입력을 받고, 자료를 저장하며, API를 호출하고, 결과를 화면에 보여줍니다.

VS Code에서 Cline이나 Copilot을 사용해 코드를 만드는 작업과 완성된 검색기가 OpenRouter 또는 다른 모델 API를 호출하는 작업은 별개입니다. 편집기에서 사용할 수 있는 구독이나 무료 사용량이 검색기용 API 호출량으로 자동 전환되지 않습니다. 수업에서는 개발 도구의 사용량과 프로그램 API의 사용량을 구분합니다.

Codex, Antigravity, Copilot, Cline, OpenCode 같은 도구는 같은 작업 요청서를 이용해 대체할 수 있습니다. 교육생은 이미 사용할 수 있는 도구 하나를 주 경로로 선택합니다. Ollama처럼 로컬에서 모델을 실행하는 경로는 사전에 모델을 내려받고 실행 속도를 확인한 경우에만 사용합니다. 도구 이름보다 파일 수정, 명령 실행, 오류 복구가 가능한지가 중요합니다.

워크플로우에서 확인할 지점

코딩 에이전트는 개발 과정에서 파일을 만들고 고치는 역할을 맡고, 완성된 업무 프로그램은 운영 과정에서 자료를 읽고 결과를 보여줍니다. 모델 API는 프로그램이 고른 맥락을 해석하는 한 단계입니다. 이 세 역할을 구분하면 개발 도구를 바꾸더라도 자료의 저장 위치, 외부 전송 범위, 실행 결과의 검증 기준을 유지할 수 있습니다.

여러 코딩 도구를 비교할 때에는 생성 속도보다 업무 장면을 얼마나 정확히 이해했는지, 원본 보호와 오류 처리를 코드에 반영했는지, 사용자가 결과를 다시 확인할 수 있는지를 봅니다. 도구 선택은 이러한 작업 흐름을 안정적으로 수행하기 위한 수단입니다.

바이브코딩의 기본 단위를 정한다

바이브코딩 요청에는 사용자 장면, 입력 자료, 처리 과정, 결과 형태, 데이터 보관 위치, 실패 처리와 검증 절차가 들어가야 합니다. “정책 검색기를 만들어 줘”라고만 요청하면 코딩 에이전트는 저장소와 검색 방식, 외부 전송 범위를 임의로 선택할 수 있습니다.

기관 프로젝트에서는 자료가 어디에서 와서 어디로 이동하는지가 가장 먼저 정해져야 합니다. 공개자료와 내부자료를 구분하고, 원본을 변경하는지, 외부 API에 어떤 문장을 보내는지, 결과를 어디에 저장하는지 씁니다. 이 내용이 있으면 기술 스택이 바뀌어도 프로젝트의 경계를 유지할 수 있습니다.

기능은 문서 목록, 본문 읽기, 구조화, 검색, 답변 생성처럼 검증 가능한 단위로 나눕니다. 각 단위는 같은 예제 자료로 다시 실행할 수 있어야 합니다. 오류를 설명할 때도 기대한 결과와 실제 결과, 최근 변경을 연결하면 에이전트가 문제의 위치를 좁힐 수 있습니다.

4장 PowerShell로 자료 목록과 출처대장을 만든다

AI를 호출하기 전에 처리 대상을 확정한다

PowerShell은 Windows에서 파일과 명령을 반복 처리하는 작업 환경입니다. 기관 문서 프로젝트의 첫 단계는 파일을 요약하는 일이 아니라 어떤 파일이 있는지 확인하는 일입니다. 파일명, 확장자, 크기, 수정시각과 경로를 목록으로 만들면 이후 처리 결과를 원본과 비교할 수 있습니다.

출처대장에는 각 파일을 식별하는 ID를 추가합니다. 문서를 어디에서 받았는지, 자료 유형은 무엇인지, 기준일은 언제인지, 공개자료인지 가상자료인지 기록합니다. 이 정보는 나중에 검색 결과의 출처와 원문 위치를 표시할 때 그대로 사용됩니다.

파일 자동화의 원리와 적용 범위

PowerShell 단계의 핵심은 문서 내용을 해석하는 데 있지 않습니다. 처리할 파일을 확정하고, 각 파일에 출처 ID를 부여하며, 같은 폴더를 다시 조사해도 결과가 흔들리지 않게 만드는 데 있습니다. 이 목록은 뒤에서 추출이나 검색이 잘못됐을 때 어느 원본에서 문제가 시작됐는지 추적하는 기준이 됩니다.

워크플로우는 읽기 전용 조사를 기본으로 삼습니다. 지원할 확장자를 먼저 정하고, 한글과 공백이 포함된 경로를 그대로 보존하며, 목록의 행 수를 실제 파일 수와 비교합니다. 이런 결정적 처리는 AI가 맡기기보다 스크립트가 맡는 편이 안정적입니다.

PowerShell 결과는 첫 번째 맥락 데이터가 됩니다. 아직 문서 본문을 읽지 않았지만, 어떤 자료가 있고 언제 수정됐는지 질문에 답할 수 있습니다. 다음 단계에서는 Python으로 문서 본문을 읽고 구조화된 결과를 만듭니다.

5장 VBA는 익숙한 엑셀 업무와 AI 자동화를 연결한다

표 안에서 반복되는 판단을 밖으로 꺼낸다

VBA는 오래된 기술처럼 보이지만, 공공기관에서 여전히 널리 사용하는 엑셀 업무와 자동화를 연결하는 현실적인 접점입니다. 교육생이 이미 사용하는 서식과 결재용 표를 버리지 않고도 파일 선택, 행 정리, 값 검증, 결과 내보내기 같은 반복 작업을 매크로로 묶을 수 있습니다.

VBA가 맡을 일과 언어모델이 맡을 일은 구분해야 합니다. 셀의 값과 형식을 검사하고 정해진 규칙으로 행을 옮기는 일은 VBA가 안정적으로 처리합니다. 문장의 의미를 분류하거나 보고 문구의 초안을 만드는 일은 필요한 셀과 근거만 골라 모델 API에 전달할 수 있습니다.

Supabase는 여러 사람이 같은 근거와 검수 상태를 공유할 때 사용할 수 있습니다. PostgreSQL의 표, JSONB, 전문검색과 벡터 검색을 하나의 저장소에서 구성할 수 있습니다. 공개 가능한 키가 있더라도 모든 행을 읽게 해서는 안 되며, 사용자의 역할에 따라 행 단위 접근 정책을 적용합니다.

Cloudflare Worker는 공개 RSS를 가져오거나 모델 API를 중계하는 작은 서버 기능으로 사용할 수 있습니다. 비밀 키는 Worker의 비밀 설정에 보관합니다. 예약 실행은 공개자료 갱신에 사용할 수 있지만, 설정을 저장한 것과 실제 실행에 성공한 것은 구분해야 합니다.

공공기관의 판단을 위한 Context Injection

RAG는 Retrieval-Augmented Generation의 약자입니다. 외부 자료에서 질문과 관련된 정보를 가져와 언어모델의 답변 생성에 사용하는 구조를 가리킵니다. 검색 단계는 벡터 검색일 수도 있지만 SQL, 전문검색, 파일 선택, API 호출 또는 MCP 도구 호출일 수도 있습니다.

임베딩 기반 Vector RAG가 널리 알려지면서 RAG와 벡터 데이터베이스를 같은 의미로 사용하는 경우가 있습니다. 그러나 기관 업무에서는 법령 조문처럼 정확한 문자열이 중요한 질문, 예산과 건수처럼 SQL 계산이 필요한 질문, 최신 공지를 API로 가져와야 하는 질문이 함께 존재합니다. 모든 질문을 벡터 검색 하나로 처리하면 오히려 정확도가 떨어질 수 있습니다.

공공기관에서 Context Injection이 필요한 이유는 모델이 기관의 현재 상황을 자동으로 알 수 없기 때문입니다. 기관의 내규와 회의자료, 지자체 의회 회의록, 상위기관의 정책 발표, 최근 언론 보도는 서로 다른 시점과 권위를 가집니다. 기관장이 회의와 브리핑을 준비할 때에는 이 자료를 많이 보여주는 것보다 질문에 맞는 근거를 골라 기준일과 출처를 함께 전달하는 일이 중요합니다.

기관의 질문을 분류한다

정적·파일·SQL·키워드·벡터·API·도구 검색 중 하나를 선택한다

검색된 근거를 출처와 기준일로 정리한다

정리된 Context와 질문을 언어모델에 전달한다

임베딩을 넘어 맥락을 고르는 기준

이 교재는 맥락주입을 여덟 가지 방식으로 나눕니다. 정적 맥락은 작고 변하지 않는 정보를 직접 제공합니다. 파일 맥락은 선택한 문서를 읽습니다. 구조화 맥락은 SQL과 JSON으로 정확한 값을 조회합니다. 어휘 검색은 FTS와 BM25로 단어가 일치하는 문단을 찾습니다.

의미 검색은 임베딩으로 표현이 다른 관련 문단을 찾습니다. 하이브리드 검색은 여러 검색 결과를 결합합니다. 동적 맥락은 RSS와 API로 최신 정보를 가져옵니다. 도구 맥락은 MCP를 통해 인공지능이 검색 기능을 호출하게 합니다. 다음 장부터 각 방식을 하나씩 분리해 살펴봅니다.

방식의 정의

정적 맥락주입은 인공지능이 항상 알아야 하는 작은 정보를 System Prompt나 고정된 설정에 넣는 방식입니다. 기관의 역할, 답변 형식, 용어 정의, 금지 규칙처럼 분량이 작고 자주 바뀌지 않는 내용에 적합합니다.

기관의 고정 정보와 답변 규칙을 작성한다

서비스가 질문 앞에 정적 Context를 붙인다

언어모델이 같은 규칙으로 답변을 생성한다

기관 적용 사례

정책 브리핑 보조자에게 기관명, 담당 사업, 답변의 기본 형식을 알려줄 수 있습니다. 답변에는 확인된 사실, 기관 관련성, 추가 확인 사항과 근거 위치를 구분하도록 지정합니다. 문서에 없는 승인 여부와 시행일을 추정하지 않도록 규칙을 둡니다.

정적 맥락에 전체 내규와 회의록을 넣으면 호출할 때마다 같은 긴 내용을 반복 전송하게 됩니다. 내용이 바뀌었을 때 어느 부분을 수정해야 하는지도 관리하기 어렵습니다. 정적 맥락은 답변의 행동 규칙과 작은 기관 프로필에 제한합니다.

적용 범위와 선택 기준

정적 맥락은 기관의 역할과 답변 원칙처럼 작고 안정적인 정보를 모든 질문에 공통으로 적용할 때 적합합니다. 기관 프로필을 넣기 전과 뒤의 답변을 비교하면 모델의 일반 지식이 기관의 관점과 표현 방식으로 좁혀지는 원리를 확인할 수 있습니다. 다만 제공하지 않은 사실까지 기관 정보인 것처럼 생성되는지는 별도로 살펴야 합니다.

문서 본문과 최신 현안처럼 자주 바뀌는 자료는 정적 맥락에 계속 덧붙이지 않습니다. 정적 맥락은 모델의 행동과 출력 구조를 정하고, 실제 근거는 파일이나 검색 결과를 통해 질문마다 다르게 주입하는 것이 관리에 유리합니다.

구현 스택, 이렇게 작동합니다
만들어지는 것독립 제품이 아니라 모든 챗봇·프로그램 안에 들어가는 기본 설정층
작동 원리변하지 않는 기관 용어와 답변 원칙을 질문보다 먼저 모델 입력에 붙인다
실행 흐름YAML·JSON 기준 읽기 → 시스템 메시지 조립 → 사용자 질문 추가 → LLM 답변
예시 결과기관 약어와 답변 금지사항을 항상 지키는 내부 챗봇

2장 File Context는 선택한 문서 내용을 직접 제공한다

방식의 정의

파일 맥락주입은 TXT, Markdown, JSON 또는 추출된 문서 텍스트를 읽어 질문과 함께 전달하는 방식입니다. 문서가 몇 건뿐이고 전체 내용이 짧을 때 별도의 검색 시스템 없이 빠르게 적용할 수 있습니다.

사용자가 파일을 선택한다

프로그램이 텍스트와 문서정보를 읽는다

필요한 절 또는 전체 내용을 Context로 만든다

질문과 함께 언어모델에 전달한다

기관 적용 사례

기관 소개 파일, 짧은 업무 지침, 행사 운영 기준, 자주 묻는 질문을 파일로 관리할 수 있습니다. 사용자가 “출장 승인 절차를 알려 달라”고 물으면 관련 지침 파일을 읽어 답변 맥락으로 넣습니다. 문서명과 개정일을 함께 제공해야 답변의 기준을 확인할 수 있습니다.

파일 수와 분량이 늘어나면 모든 문서를 매번 읽을 수 없습니다. 같은 규정의 여러 버전이 섞일 수도 있습니다. 파일 맥락은 작은 자료 묶음의 출발점이며, 규모가 커질 때 검색 방식으로 전환합니다.

적용 범위와 선택 기준

파일 맥락은 기관 프로필과 짧은 내규처럼 전체를 읽어도 입력 한도를 넘지 않는 자료에 적합합니다. 파일을 교체하면 답변의 기준일과 근거 위치도 함께 바뀌어야 합니다. 문서가 많아져 질문과 무관한 내용까지 매번 전달하게 되면 어휘 검색이나 의미 검색으로 필요한 부분만 고르는 구조로 전환합니다.

브라우저에서 파일을 읽는다는 사실만으로 자료가 로컬에 남는 것은 아닙니다. 이후 모델 호출이 있다면 선택한 본문이 외부 API로 전송될 수 있으므로, 파일 읽기와 모델 전송을 워크플로우에서 구분해 표시해야 합니다.

구현 스택, 이렇게 작동합니다
만들어지는 것파일 업로드가 있는 로컬 웹앱 또는 데스크톱 도구
작동 원리선택한 PDF·DOCX의 내용을 추출해 검색 DB 없이 질문과 함께 모델에 바로 보낸다
실행 흐름파일 선택 → 텍스트 추출 → 길이·형식 정리 → 질문과 함께 LLM 전달
예시 결과한 개의 회의자료를 올리고 안건·쟁점·기관 영향을 묻는 검토 도구

3장 Structured Context는 JSON과 SQL에서 정확한 값을 조회한다

방식의 정의

구조화 맥락주입은 표의 행과 열, JSON의 필드처럼 미리 정한 구조에서 필요한 값을 조회해 인공지능에 제공하는 방식입니다. 합계, 기간, 담당부서, 진행 상태와 같이 계산과 필터가 중요한 질문에 적합합니다.

질문에서 날짜·기관·상태 조건을 찾는다

SQL 또는 JSON 필터로 정확한 행을 조회한다

조회값과 원문 문서 ID를 Context로 만든다

언어모델이 결과를 설명한다

기관 적용 사례

회의 안건 테이블에 회의일, 안건명, 담당부서, 결정 상태와 후속 기한을 저장했다고 가정합니다. “이번 달 미완료 과제는 몇 건인가”라는 질문은 SQL로 계산합니다. 언어모델은 계산을 반복하지 않고 조회 결과와 근거 문서 목록을 읽기 좋은 문장으로 설명합니다.

자연어를 SQL로 바꾸는 NL2SQL을 사용할 때는 읽기 전용 조회만 허용합니다. 사용할 수 있는 테이블과 컬럼, 상태값을 미리 알려주고 수정·삭제 명령을 차단합니다. 구조화 데이터에 없는 예외와 논의 과정은 원문 문단에서 다시 찾아야 합니다.

적용 범위와 선택 기준

구조화 맥락은 질문의 답이 행, 열, 날짜 조건과 집계로 표현될 때 우선합니다. 미완료 건수나 담당부서별 목록을 언어모델이 문서에서 추정하게 하지 않고 데이터베이스가 계산하게 하면 결과의 재현성이 높아집니다. 언어모델은 조회값을 설명하는 역할을 맡습니다.

표의 각 행에는 원문 문서 ID를 남겨야 합니다. 숫자와 상태의 근거를 원문에서 다시 확인할 수 있어야 하기 때문입니다. 반대로 논의 배경과 조건처럼 표에 담기 어려운 내용은 구조화 조회만으로 답하지 않고 관련 문단을 함께 검색합니다.

구현 스택, 이렇게 작동합니다
만들어지는 것DB가 연결된 백엔드 웹앱 또는 정기 보고 프로그램
작동 원리언어모델이 계산하지 않고 SQL이 정확한 행과 숫자를 조회한 뒤 그 결과만 설명에 사용한다
실행 흐름질문에서 기간·부서 추출 → SQL 조회 → JSON 검증 → LLM 설명
예시 결과최근 3개월 사업별 예산 집행액을 조회하고 차이를 설명하는 사이트

4장 Pre-analysis Context는 문서를 JSON으로 먼저 분석한다

방식의 정의

문서 사전구조화는 PDF나 회의록을 저장할 때 언어모델 또는 파서가 주요 항목을 JSON으로 추출하는 방식입니다. 원문 전체를 검색하는 것과 별도로 기관, 날짜, 안건, 담당부서, 상태, 기한을 구조화해 빠르게 조회할 수 있습니다.

원본 문서와 추출 텍스트를 보존한다

정해진 Schema로 주요 항목을 추출한다

사람이 원문과 JSON을 비교해 승인한다

승인된 JSON을 SQL과 검색 필터에 사용한다

기관 적용 사례

위원회 회의록에서 회의일, 안건, 결정 상태와 담당부서를 추출합니다. 업무보고에서는 사업명, 예산, 일정, 진행 상태를 추출할 수 있습니다. 문서 유형마다 필요한 필드가 다르므로 하나의 거대한 Schema보다 유형별 Schema를 사용하는 편이 관리하기 쉽습니다.

JSON은 원문의 모든 의미를 담지 못합니다. 처음 정한 필드에 없는 운영상의 문제나 조건은 구조화 결과에서 사라집니다. 원본 파일, 전체 텍스트, 구조화 JSON, 검색 문단과 인덱스를 함께 보관하는 Multi-Representation 구조가 필요합니다.

적용 범위와 선택 기준

사전구조화는 같은 유형의 문서가 반복해서 들어오고, 안건·담당부서·상태·기한을 자주 비교할 때 효과적입니다. Schema는 무엇을 찾을 수 있게 하는 동시에 무엇을 버릴지를 결정합니다. 날짜와 담당부서만 추출한 구조에서는 결정 상태를 묻는 질문에 답할 수 없습니다.

따라서 구조화 JSON을 원문의 대체물로 보지 않습니다. 추출값마다 근거 문장과 원문 위치를 연결하고, Schema 밖의 질문이 들어오면 전체 텍스트 검색으로 돌아갈 수 있어야 합니다. 문서 유형이 다르면 각각의 질문에 맞는 Schema를 사용합니다.

구현 스택, 이렇게 작동합니다
만들어지는 것백그라운드 문서 처리 프로그램과 그 결과를 읽는 검색 사이트
작동 원리문서가 들어올 때 한 번 분석해 기관·날짜·쟁점·결정사항을 JSON으로 저장한다
실행 흐름새 문서 감지 → 파싱 → LLM 사전분석 → 검토·저장 → 질문 시 필터 검색
예시 결과수백 건의 회의록을 안건과 결정사항 기준으로 빠르게 찾는 시스템

5장 Lexical Retrieval은 FTS와 BM25로 정확한 단어를 찾는다

방식의 정의

어휘 검색은 질문과 문서에 실제로 나타난 단어를 기준으로 관련 문단을 찾습니다. Full Text Search는 문서를 단어 단위로 색인합니다. BM25는 검색어의 빈도, 단어의 희귀성, 문서 길이를 반영해 결과의 관련도를 계산합니다.

문서 문단을 단어 색인에 등록한다

질문에서 법령명·조문·기관명·사업명을 찾는다

BM25 점수로 관련 문단의 순위를 정한다

상위 문단과 원문 위치를 Context로 만든다

기관 적용 사례

법령명, 조문번호, 회의 안건명, 기관명, 사건번호는 정확한 문자열이 중요합니다. “생활안전 조례 제12조”를 찾을 때 의미가 비슷한 조문보다 해당 명칭과 번호가 있는 문단을 먼저 보여줘야 합니다. SQLite FTS5와 PostgreSQL 전문검색을 사용할 수 있습니다.

BM25 점수가 높다고 답이 확정되는 것은 아닙니다. 관련 단어가 많이 포함됐다는 뜻입니다. 결과 화면에는 점수보다 문서명, 조문번호, 시행일, 앞뒤 문맥과 원문 위치를 먼저 보여줍니다. 개정 전 문서가 함께 검색되면 기준일로 구분합니다.

적용 범위와 선택 기준

어휘 검색은 법령명, 조문번호, 부서명, 사업명처럼 정확한 표기가 답의 위치를 가리킬 때 우선합니다. 사용자의 질문과 문서가 같은 단어를 공유할수록 강합니다. 결과가 약할 때에는 동의어를 무작정 늘리기보다 제목과 본문의 가중치, 문단 분리, 형태소 처리와 기준일 필터를 먼저 살펴봅니다.

성능은 대표 질문에서 기대 문단이 상위 결과에 포함되는지로 판단합니다. BM25 점수 자체는 관련성의 단서일 뿐 사실의 신뢰도나 최신성을 보장하지 않으므로, 출처 정보와 문서 상태를 별도로 유지합니다.

구현 스택, 이렇게 작동합니다
만들어지는 것로컬 검색기 또는 서버형 문서검색 사이트
작동 원리문단에 등장한 정확한 단어를 색인하고 질문과 많이 겹치는 문단에 높은 점수를 준다
실행 흐름문단 분할 → FTS5·BM25 색인 → 키워드 검색 → 날짜·부서 필터 → 상위 문단
예시 결과법령명·조문번호·사업명으로 원문을 정확히 찾는 검색기

6장 Semantic Retrieval은 Vector RAG로 표현이 다른 문단을 찾는다

방식의 정의

의미 검색은 문장에 포함된 단어가 다르더라도 내용이 유사한 문단을 찾습니다. 임베딩 모델은 문단과 질문을 숫자 배열로 변환합니다. 검색 프로그램은 질문 벡터와 가까운 문단 벡터를 찾아 결과로 반환합니다.

문서를 의미 단위의 문단으로 나눈다

임베딩 모델이 각 문단을 벡터로 변환한다

질문도 같은 모델로 벡터화한다

가까운 문단을 찾아 Context로 제공한다

기관 적용 사례

사용자는 “몸이 불편한 주민의 이동 지원”이라고 질문하고 문서에는 “교통약자 이동편의 증진”이라고 기록돼 있을 수 있습니다. 정확한 단어가 일치하지 않아도 의미 검색은 관련 문단을 찾을 수 있습니다. 유사 민원과 정책 취지를 탐색할 때 유용합니다.

Vector RAG는 법령번호, 예산, 날짜처럼 정확한 값의 검색을 보장하지 않습니다. 임베딩 모델과 문단 분리 방식에 따라 결과가 달라지고 외부 임베딩 API를 사용하면 문단이 외부로 전송될 수 있습니다. 의미 검색이 필요한 질문이 실제로 있는지 먼저 확인합니다.

적용 범위와 선택 기준

의미 검색은 사용자의 표현과 행정문서의 표현이 다를 때 유용합니다. 민원 언어와 정책 용어를 연결하거나 유사 사례를 탐색하는 질문이 대표적입니다. 같은 뜻을 다른 말로 표현한 질문에서 어휘 검색과 벡터 검색의 결과를 비교하면 의미 검색이 필요한 범위를 확인할 수 있습니다.

법령번호와 날짜, 예산처럼 한 글자의 차이가 중요한 값은 벡터 유사도에 맡기지 않습니다. 의미 검색의 결과도 출처와 원문 위치를 포함해야 하며, 임베딩 모델과 문단 분리 방식이 바뀌면 검색 결과가 달라질 수 있음을 운영 기록에 남깁니다.

구현 스택, 이렇게 작동합니다
만들어지는 것벡터 저장소가 연결된 로컬 또는 클라우드 검색 사이트
작동 원리질문과 문단을 숫자 벡터로 바꾸고 의미상 가까운 문단을 거리 계산으로 찾는다
실행 흐름문단 청킹 → 임베딩 생성 → FAISS·pgvector 저장 → 질문 벡터 검색 → 원문 반환
예시 결과표현이 다른 민원과 정책 문장 사이의 유사 내용을 찾는 검색기

7장 Hybrid Retrieval은 정확한 단어와 의미를 함께 사용한다

방식의 정의

하이브리드 검색은 어휘 검색과 의미 검색, 필요하면 구조화 필터를 함께 사용합니다. 질문에 날짜 조건과 법령명이 있으면 먼저 해당 기간과 자료 유형을 좁힙니다. 이후 BM25와 벡터 검색 결과를 합쳐 관련 문단을 정합니다.

메타데이터와 SQL 조건으로 자료 범위를 좁힌다

BM25가 정확한 단어의 문단을 찾는다

Vector Search가 의미가 가까운 문단을 찾는다

중복을 제거하고 순위를 결합한다

기관 적용 사례

“최근 의회에서 논의된 교통약자 지원의 법적 근거를 찾아 달라”는 질문에는 최근 회의라는 날짜 조건, 의회 자료라는 유형, 교통약자라는 의미, 법적 근거라는 법령 키워드가 함께 있습니다. 하나의 검색 방식보다 여러 신호를 순서대로 사용하는 편이 적합합니다.

두 검색의 점수 범위가 다르므로 점수를 단순히 더하지 않습니다. 각 검색의 순위를 결합하거나, 법령번호와 같은 정확한 일치에 가중치를 줍니다. 기대 근거가 있는 질문 세트로 가중치와 결과 수를 평가합니다.

적용 범위와 선택 기준

하이브리드 검색은 정확한 명칭과 의미적 유사성이 한 질문에 함께 들어 있을 때 선택합니다. 두 검색 결과를 단순히 합치는 데서 끝나지 않고 중복을 제거하고, 정형 조건과 정확한 일치를 우선하며, 의미 검색 결과를 보완적으로 배치합니다.

최종 순위의 이유를 설명할 수 있어야 합니다. 법령명이 일치해 위로 올라왔는지, 질문과 의미가 가까워 포함됐는지, 최근 자료로 범위를 좁혔는지를 기록하면 검색 오류를 수정할 수 있습니다. 검색 신호가 늘어날수록 질문 세트에 의한 검증이 더 중요해집니다.

구현 스택, 이렇게 작동합니다
만들어지는 것BM25와 벡터 검색을 함께 쓰는 기관 문서검색 사이트
작동 원리정확한 단어 검색 결과와 의미 검색 결과를 따로 구한 뒤 순위와 필터를 결합한다
실행 흐름BM25 후보 + Vector 후보 → 기간·기관 필터 → RRF·가중 결합 → 재순위화
예시 결과조문번호는 정확히 찾고 유사한 회의 발언까지 함께 제시하는 검색기

8장 Dynamic Context는 RSS와 API로 최신 자료를 가져온다

방식의 정의

동적 맥락주입은 질문 시점에 맞춰 RSS, 공개 API, 데이터베이스에서 최신 정보를 가져오는 방식입니다. 모델의 학습 시점 이후에 발표된 정책, 오늘 등록된 공지, 최근 회의 안건을 답변에 포함할 때 사용합니다.

허용된 RSS와 API에서 새 자료를 수집한다

발행시각·수집시각·출처를 저장한다

기관 프로필과 관련된 항목을 검색한다

최신 근거와 기존 기관 문서를 함께 제공한다

기관 적용 사례

상위기관의 공모 공지가 새로 등록되면 제목과 URL, 발행시각을 저장합니다. 기관 프로필의 담당 사업과 관련된 항목을 찾고, 내부 업무보고와 내규를 함께 검색합니다. 기사나 공지에서 확인된 사실과 기관이 추가로 검토할 사항을 구분합니다.

브라우저에서 RSS를 직접 읽으면 CORS로 실패할 수 있습니다. Python, Node.js 또는 Worker가 허용된 주소만 수집하도록 구성합니다. 수집 실패 시 기존 자료를 삭제하지 않고 마지막 성공시각과 실패 상태를 표시합니다.

적용 범위와 선택 기준

동적 맥락은 답변 시점이 품질을 좌우하는 질문에 사용합니다. 새 공고와 보도자료, 최근 회의 안건은 발행시각과 수집시각을 함께 기록하고 같은 URL이나 문서 ID의 중복을 제거해야 합니다. 수집 경로가 실패하면 마지막 성공 자료와 실패 상태를 구분해 보여줍니다.

최신 자료가 항상 가장 권위 있는 근거는 아닙니다. 뉴스와 공지는 현안의 변화를 보여주고, 법령과 내규는 적용 기준을 제공합니다. Context Builder는 자료 유형과 기준일을 유지한 채 두 근거의 역할을 구분해야 합니다.

구현 스택, 이렇게 작동합니다
만들어지는 것정기 수집 프로그램과 최신 현황을 보여주는 사이트
작동 원리스케줄러가 RSS·공공 API를 반복 호출해 새 자료만 저장하고 질문 시 최신 기준일을 함께 넘긴다
실행 흐름예약 실행 → RSS·API 수집 → 중복 제거 → DB 갱신 → 질문 시 최신 자료 검색
예시 결과기관 관련 보도와 상위기관 공지를 자동 갱신하는 현안 모니터

9장 Query Router는 질문에 맞는 맥락 경로를 고른다

방식의 정의

Query Router는 질문의 표현과 목적을 분석해 어떤 검색 기능을 사용할지 결정합니다. 모든 질문에 모든 검색을 실행하면 비용과 시간이 늘고 관련 없는 결과가 섞일 수 있습니다. 처음에는 명확한 규칙으로 구현하고 필요할 때 모델 분류를 추가합니다.

질문에서 조문·숫자·날짜·최신성 표현을 찾는다

SQL·BM25·Vector·RSS·MCP 중 우선 경로를 고른다

검색 결과가 부족하면 보조 경로를 실행한다

선택한 경로와 결과를 기록한다

기관 적용 사례

‘제○조’가 있으면 법령 전문검색을 우선합니다. ‘몇 건’, ‘총액’, ‘담당부서’가 있으면 SQL을 사용합니다. ‘유사한 사례’는 벡터 검색을 사용하고, ‘최근 발표’는 RSS와 공개 API를 확인합니다. 질문에 여러 신호가 있으면 정형 조건으로 범위를 좁힌 뒤 문서검색을 실행합니다.

라우터가 잘못된 경로를 고를 수 있으므로 사용자가 검색 범위를 바꿀 수 있게 합니다. 검색 결과가 없을 때 다른 경로로 자동 확장했는지도 화면에 표시합니다.

적용 범위와 선택 기준

Query Router는 검색 경로가 여러 개이고 질문의 신호를 비교적 분명하게 구분할 수 있을 때 필요합니다. 조문 표기, 집계 표현, 유사 사례, 최신성 표현처럼 설명 가능한 규칙으로 시작하면 어떤 경로가 선택됐는지 추적하기 쉽습니다. 규칙만으로 모호한 질문이 많을 때 모델 분류를 보조적으로 붙입니다.

라우터의 품질은 답변 문장보다 올바른 검색 경로를 선택했는지로 평가합니다. 신호가 충돌하면 구조화 조건으로 범위를 좁힌 뒤 문서검색을 수행하고, 사용자가 검색 범위를 바꿀 수 있게 합니다.

구현 스택, 이렇게 작동합니다
만들어지는 것사용자에게는 보이지 않는 검색 사이트의 백엔드 판단 모듈
작동 원리질문의 종류를 판별해 SQL·BM25·Vector·RSS 가운데 필요한 검색 경로만 선택한다
실행 흐름질문 분류 → 검색 경로 선택 → 도구 실행 → 결과 합치기 → Context Builder 전달
예시 결과예산 질문은 SQL로, 법령은 BM25로, 유사 사례는 Vector로 보내는 라우터

10장 Context Builder는 검색 결과를 답변 가능한 입력으로 만든다

방식의 정의

Context Builder는 여러 검색 결과를 최종 언어모델 입력으로 정리합니다. 중복 문단을 제거하고, 질문의 시점과 맞지 않는 자료를 구분하며, 사용 권한과 입력 길이를 확인합니다. 각 근거에는 문서 ID, 제목, 자료 유형, 기준일, 원문 위치를 붙입니다.

여러 검색 경로의 결과를 모은다

중복·권한·기준일을 검사한다

질문에 직접 필요한 근거부터 배열한다

답변 규칙과 근거 ID를 포함해 모델에 전달한다

기관 적용 사례

최신 회의록과 과거 계획서가 함께 검색되면 두 자료의 기준일과 상태를 분리합니다. ‘검토 중’과 ‘완료’를 같은 현재 상태로 합치지 않습니다. 문단이 너무 짧아 조건이 빠졌다면 앞뒤 문단을 함께 가져옵니다.

답변 형식은 확인된 사실, 기관과의 관련성, 추가 확인 항목, 근거 목록으로 정합니다. 모델이 인용한 근거 ID가 실제 입력에 있는지 검사합니다. 입력에 없는 날짜와 예산을 생성하면 답변을 반려합니다.

적용 범위와 선택 기준

Context Builder는 여러 검색 방식이 반환한 결과를 언어모델이 읽을 수 있는 하나의 입력으로 바꾸는 공통 단계입니다. SQL 값, 회의록 문단, RSS 항목이 함께 들어오면 중복과 기준일, 자료의 권위, 사용 권한을 확인하고 질문에 직접 필요한 근거부터 배열합니다.

맥락의 양이 많다고 답변이 좋아지는 것은 아닙니다. 오래된 계획과 최신 결과가 섞이거나 같은 문장이 반복되면 상태를 잘못 판단할 수 있습니다. 입력에 포함된 근거 ID와 모델이 답변에서 사용한 근거 ID를 비교할 수 있어야 합니다.

구현 스택, 이렇게 작동합니다
만들어지는 것검색기와 LLM 사이에서 작동하는 백엔드 조립 모듈
작동 원리여러 검색 결과의 중복을 없애고 토큰 한도 안에서 출처·날짜·원문 위치를 붙인다
실행 흐름검색 후보 수집 → 중복 제거 → 중요도 정렬 → 출처 표기 → LLM 입력 생성
예시 결과기관장 질문에 필요한 근거 문단만 묶어 답변 모델에 전달하는 조립기

11장 Tool-based Context는 MCP로 검색 기능을 호출한다

방식의 정의

MCP는 Model Context Protocol의 약자입니다. 인공지능 클라이언트가 외부 도구의 이름, 입력과 출력을 이해하고 호출할 수 있게 하는 연결 규칙입니다. MCP 서버는 검색 도구를 제공하고, MCP 클라이언트는 도구 설명을 읽어 호출합니다.

MCP 서버가 검색 도구의 입력과 출력을 설명한다

클라이언트가 질문과 도구 목록을 모델에 제공한다

모델이 필요한 도구 호출을 요청한다

도구 결과가 다시 Context로 들어간다

기관 적용 사례

`search_regulations`는 법령명과 기준일을 받아 조문과 원문 위치를 반환합니다. `search_meetings`는 안건, 기간, 기관을 받아 회의 문단과 결정 상태를 반환합니다. `query_issues`는 담당부서와 상태 조건으로 데이터베이스를 조회합니다. 각 도구는 하나의 분명한 검색 책임을 가집니다.

MCP는 검색 품질을 자동으로 높이지 않습니다. 기존 검색 기능이 잘못된 문단을 반환하면 MCP도 같은 결과를 전달합니다. 도구는 읽기 전용으로 시작하고, 허용 자료와 최대 결과 수, 기준일 처리, 반환 필드를 명시합니다.

적용 범위와 선택 기준

MCP는 이미 동작하는 검색 기능을 여러 AI 클라이언트에서 공통으로 호출하려 할 때 유용합니다. 도구 이름과 입력 Schema, 반환 JSON을 명확하게 정의하면 모델은 질문에 맞는 도구를 고르고 결과를 다시 맥락으로 사용할 수 있습니다. 반환값에는 출처와 기준일, 원문 위치가 포함되어야 합니다.

도구화는 검색 품질을 대신 만들지 않습니다. 먼저 검색 API의 결과와 실패 처리가 안정적이어야 합니다. 기관 환경에서는 읽기 전용 도구로 시작하고, 검색 실패를 빈 근거와 오류 상태로 반환해 모델이 자체 지식으로 빈자리를 채우지 않게 합니다.

프로젝트 질문을 먼저 고른다

강의 뒤 하루 프로젝트에서는 교육생이 자신의 기관에서 반복되는 질문 하나를 선택합니다. “최근 의회 지적 사항과 후속 조치는 무엇인가”, “이 사업의 법적 근거와 내부 처리 절차는 무엇인가”, “이번 달 미완료 과제와 관련 회의 근거는 무엇인가”처럼 기관장이 실제로 물을 수 있는 질문이 좋습니다.

핵심 질문 한 개와 보조 질문 네 개를 작성합니다. 각 질문에 답하려면 어떤 문서와 데이터가 필요한지 역으로 정합니다. 실제 내부자료를 사용할 수 없다면 공개자료 또는 비식별·가상자료로 같은 구조를 만듭니다. 자료의 사용 가능 여부와 외부 모델 전송 가능 여부를 구분합니다.

하루 프로젝트는 수집, 저장, 검색, 맥락 조립, 화면이라는 전체 흐름을 담되 질문과 자료의 범위를 좁혀야 합니다. 외부 모델 연결은 선택 사항이며, AI 호출이 없어도 자료 저장과 검색은 동작해야 합니다. 어떤 Context Injection 방식을 선택했는지와 그 선택이 기관장의 질문에 어떻게 연결되는지를 설명할 수 있어야 합니다.

프로젝트 결과에는 실행 가능한 화면, 승인된 예제 자료, 질문 다섯 개, 각 질문의 기대 근거, 데이터 보관 위치, 검증 기록과 3분 시연이 포함됩니다. 제목은 ‘벡터 RAG 시스템’보다 ‘의회 지적사항과 후속 조치를 찾는 브리핑 검색기’처럼 사용 장면이 드러나게 정합니다.

기관과 기관장에게 주는 가치를 확인한다

완성된 도구가 어떤 시간을 줄이는지 설명할 수 있어야 합니다. 회의 전 여러 폴더에서 문서를 다시 찾는 시간, 최신 뉴스와 기관 업무를 비교하는 시간, 질문을 받은 뒤 원문을 확인하는 시간을 줄일 수 있습니다. 답변을 대신 판단하는 것이 아니라 판단 전에 필요한 근거를 가까이 두는 도구로 설계합니다.

13장 검색 정확도와 맥락 품질을 질문 세트로 검증한다

검색이 열리는 것과 필요한 근거를 찾는 것은 다르다

기능 시험에서는 문서를 추가한 뒤 새로 고침해 자료가 남는지 확인합니다. 같은 문서를 다시 넣었을 때 중복 후보가 표시되는지 봅니다. 검색 결과에서 원문 위치가 열리는지 확인하고, RSS와 모델 API가 실패해도 로컬 검색이 계속 동작하는지 시험합니다.

맥락 품질 시험에서는 기대 근거가 있는 질문 10개를 사용합니다. 법령명과 조문번호, 숫자와 날짜, 표현이 다른 유사 질문, 최신 뉴스, 근거가 없는 질문을 포함합니다. 질문마다 기대 검색 경로와 기대 문단을 미리 적습니다.

부록 Context Injection 방식 선택을 위한 실무 질문

기술을 고르기 전에 자료와 질문을 확인한다

기관의 역할과 답변 원칙처럼 작고 변하지 않는 정보인가를 먼저 묻습니다. 그렇다면 Static Context가 출발점입니다. 문서가 몇 건뿐이고 전체를 읽어도 되는 분량이라면 File Context를 사용합니다. 숫자와 상태를 정확하게 계산해야 한다면 Structured Context를 선택합니다.

법령명과 조문번호처럼 정확한 단어가 중요한지 확인합니다. 그렇다면 FTS와 BM25가 우선입니다. 표현이 달라도 의미가 가까운 자료를 찾아야 한다면 Vector Search를 검토합니다. 두 종류의 질문이 섞이면 Hybrid Retrieval을 사용합니다.

오늘 발표된 자료가 필요한지, 인공지능이 여러 검색 기능을 선택해야 하는지도 확인합니다. 최신성이 중요하면 RSS와 API를 이용한 Dynamic Context를 사용합니다. 이미 만든 검색 기능을 여러 AI 클라이언트에서 재사용하려면 MCP 도구로 제공합니다.

어떤 방식을 선택하더라도 출처, 기준일, 원문 위치, 자료 권한, 외부 전송 범위를 보존합니다. Context Injection의 목적은 더 많은 자료를 모델에 넣는 것이 아니라 질문에 필요한 근거를 검증 가능한 형태로 제공하는 데 있습니다.
