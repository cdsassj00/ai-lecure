PART A · 어시스트 바이브 코딩 루틴 — 외부망↔내부망 코드 수령·실행 사이클 · 30MIN
외부망에서 AI에 코드 요청 → 검증 → 내부망 반입 → 실행 → 에러 시 다시 외부망
공공 내부망에서 Claude Code·Cursor를 자유롭게 쓸 수 없는 현실이 이 루틴의 출발점. 6차시 에이전트 전환 전에 어시스트의 한계를 체감하는 것이 목적.
WHY ASSIST공공 내부망 현실
내부망에서 에이전트 도구를 자유롭게 쓸 수 없다

Claude Code·Cursor·Codex는 외부 서버에 코드를 전송하고 결과를 받는 구조. 공공 내부망에서는 네트워크 차단으로 사용 불가. 이 현실이 4·5차시 "어시스트 모드"의 구조를 결정한다.

어시스트 모드4·5차시
외부망에서 AI에 코드를 "요청"해서 받아온다

ChatGPT·Claude·Gemini 채팅창에 요구사항을 입력 → AI가 코드를 생성 → 코드를 복사해 내부망에서 실행. AI가 직접 실행하지 않는다. 사람이 코드를 옮기고 실행한다. 에러가 나면 로그를 다시 외부망으로 가져가 수정 요청.

6차시 에이전트와의 차이
어시스트: 코드를 "받아서 옮긴다" / 에이전트: AI가 "직접 실행한다"

같은 결과물을 어시스트(4·5차시)와 에이전트(6차시)로 두 번 만들면서 차이를 체감하는 것이 Stage B의 설계.

5단계 사이클외부망↔내부망 코드 루틴
① 요구사항 전달 (외부망)

AI에 전달할 것: 데이터 구조(컬럼명·타입·샘플 3행) + 기대 출력(차트 종류, 보고서 형식) + 제약(오프라인 실행, 특정 라이브러리 금지, 한글 폰트 필요). 민감 데이터는 반드시 비식별화 후 전달.

② 코드 수령 + 검증

AI가 생성한 코드를 읽고 검증한다. 외부 통신 코드(requests, urllib)가 있는지, 파일 경로가 맞는지, 라이브러리가 내부망에 있는지 확인. 이해 안 되는 부분은 AI에 "이 코드의 3~5줄을 설명해줘"로 질문.

③ 내부망 반입 + 실행

코드를 복사하거나 .py 파일로 저장 → USB 또는 승인 경로로 내부망 이동 → python script.py 실행.

④ 에러 시 → 로그 복붙 → 수정 요청

에러 메시지를 통째로 복사 → 외부망 AI에 붙여넣기 → "이 에러를 수정해줘" → 수정된 코드 수령 → 다시 ③. 이 사이클을 반복하며 체질화.

⑤ 완성 → 아카이브 등록

완성된 코드 + 요구사항 + 에러 이력을 아카이브에 등록. 동일 업무 반복 시 재사용 가능.

STAGE B 핵심
어시스트의 한계를 직접 체감해야 6차시 에이전트의 가치를 안다

"에러 로그 복붙→수정 요청→다시 실행" 사이클을 10번 반복하면 "AI가 직접 실행해주면 좋겠다"는 욕구가 자연스럽게 생긴다. 그것이 6차시의 출발점.

어시스트의 한계불편한 5가지
오늘 하루 동안 체감한 어시스트 모드의 불편함
한계 ①
코드를 복사→붙여넣기→실행을 반복해야 한다

AI가 생성한 코드를 복사해서 파일에 붙여넣고, 터미널에서 실행하고, 에러가 나면 다시 복사해서 AI에 보내고... 이 수동 사이클이 10번 반복되면 지친다.

한계 ②
AI가 내 파일 시스템을 모른다

"이 CSV를 분석해줘"라고 할 때 파일 경로, 폴더 구조, 다른 파일과의 관계를 매번 설명해야 한다. AI가 직접 ls, cat을 할 수 없다.

한계 ③
에러 디버깅이 비효율적이다

에러 메시지를 복사→외부망에 붙여넣기→수정 코드 받기→다시 실행. 에이전트라면 에러를 보고 스스로 수정·재실행한다.

한계 ④
여러 파일을 동시에 수정할 수 없다

프로젝트가 커지면 app.py, utils.py, config.py, templates/... 여러 파일을 동시에 수정해야 한다. 어시스트는 한 번에 한 파일의 코드만 생성한다. 파일 간 일관성을 사람이 맞춰야 한다.

한계 ⑤
테스트·검증을 사람이 수동으로 해야 한다

코드가 맞는지 틀린지 사람이 직접 실행해서 확인. 에이전트는 테스트 코드를 자동 생성하고, 실행하고, 통과 여부를 확인한 뒤 수정까지 한다.

6차시 에이전트가 해결하는 것
복붙 없이 직접 실행, 파일 시스템 읽기, 자동 디버그, 멀티파일 수정, 자동 테스트

Claude Code·Cursor·Antigravity가 하는 일: ① 프로젝트 폴더를 통째로 읽는다 ② 코드를 직접 작성한다 ③ 터미널에서 실행한다 ④ 에러를 보고 스스로 수정한다 ⑤ 여러 파일을 동시에 수정한다 ⑥ 테스트를 자동 실행한다. 어시스트에서 느낀 불편함이 전부 해소된다.

이 순서가 중요한 이유
어시스트의 한계를 체감한 뒤에 에이전트를 만나야 그 가치를 안다

처음부터 에이전트를 쓰면 "당연히 되는 것"이라 느낀다. 어시스트로 고생한 뒤에 에이전트를 쓰면 "아, 이게 이렇게 편해지는구나"를 체감. 이것이 4→6차시 순서의 설계 의도.

Stage A(재료 창고)에서 Stage B(어시스트 코딩)로 전환했다. 코드를 처음 만지기 시작한 회차. 불편함이 곧 6차시의 동기.
SUMMARY오늘의 핵심 3가지
01
어시스트 바이브 코딩 루틴 체화

외부망에서 AI에 코드 요청 → 검증 → 내부망 반입 → 실행 → 에러 시 다시 외부망. 비식별화 원칙. 이 사이클이 4·5차시의 공통 토대.

02
데이터 시각화·분석 7개 모듈

Python(matplotlib·seaborn·plotly), HTML/JS(Chart.js·ECharts·D3), Power BI, pandas, scikit-learn, 딥러닝, 보고서 자동화. 상황에 맞는 도구 선택 판단.

03
어시스트의 한계 5가지를 체감

복붙 반복, 파일 시스템 무지, 비효율 디버깅, 단일 파일 한계, 수동 테스트. 이 불편함이 6차시 에이전트의 출발점.

CORE MESSAGE
코드를 직접 쓰지 않았다 — AI에 요청해서 받고 실행했다

4차시는 "코딩 수업"이 아니라 "AI와 협업해서 코드를 만드는 수업"이다. 거점리더는 코드를 쓰는 사람이 아니라, 코드가 필요한 순간에 AI에 정확히 요청하는 사람.

STAGE B · 진행중
4~5차시 = 어시스트로 코드를 받아 내부망에서 실행

Stage A: 코드 없이 서비스 체인(1~3차시). Stage B: 어시스트로 코드 수령·실행(4~5차시). Stage C: 에이전트가 직접 실행(6~8차시). 같은 과제를 3단계로 경험하면서 각 단계의 가치와 한계를 체감.
