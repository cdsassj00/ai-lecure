예를 들어 “우리 기관 문서를 검색해서 답해주는 AI 챗봇”을 만든다고 해보겠습니다. AI만 있으면 될 것 같지만 실제로는 그렇지 않습니다. AI가 답하려면 먼저 어떤 문서를 읽을지, 문서를 어떤 형식으로 정리할지, 질문이 들어오면 어떤 문서를 찾아낼지, 그 결과를 어디에서 AI에게 보낼지, 사용자가 답변을 어떤 화면에서 볼지가 필요합니다.

바이브코딩은 한 줄의 흐름으로 이해하면 됩니다

복잡한 기술도 “데이터가 들어와서 답변이 나갈 때까지 어디를 거치는가?”로 보면 단순해집니다.

① 문제

사용자가 무엇을 하려는가? 예: “기관 지침에서 출장비 기준을 찾아줘.”

② 데이터

그 답을 어디에서 찾을 수 있는가? PDF, 홈페이지, RSS, 엑셀, DB, 외부 API 등.

③ 파싱

PDF나 Word처럼 사람이 보는 문서를 AI와 프로그램이 다루기 쉬운 텍스트·XML·JSON으로 바꿉니다.

④ 저장

XML, JSON, CSV, SQLite, PostgreSQL 같은 그릇에 정리합니다.

⑤ 검색

SQL, BM25, Fuse.js, FTS5, 임베딩 중에서 질문에 맞는 방식을 선택합니다.

⑥ 컨텍스트

검색된 결과 중 필요한 부분만 AI에게 건넵니다.

⑦ AI + 화면

AI가 근거를 읽고 답하고, 사용자는 웹 화면이나 데스크톱 앱에서 결과를 봅니다.

예시로 한 번 이어보면

출장규정 PDF → Docling으로 문서 구조 추출 → SQLite에 제목·조항·본문 저장 → “식비”를 FTS5/BM25로 검색 → 상위 5개 조항을 OpenRouter AI에 전달 → AI가 “근거 조항과 함께” 답변 → HTML 화면에 표시.

이게 바로 바이브코딩 워크플로우입니다. Python, Node.js, React 같은 기술명은 이 흐름의 특정 칸을 구현하는 도구일 뿐입니다.
프로젝트를 시작할 때 기술명이 아니라 질문부터 적으세요

“React로 만들까, Python으로 만들까?”보다 먼저 “누가, 어떤 화면에서, 어떤 데이터를 가지고, 어떤 결과를 얻고 싶은가?”를 한 문장으로 적습니다. 그러면 필요한 기술이 자연스럽게 뒤에서 따라옵니다.

예: “기관장이 내부 정책문서를 질문하면 5초 안에 근거 문서와 페이지까지 보여주는 검색도구.”

이 문장만 있어도 데이터는 ‘정책문서’, 검색은 ‘근거 문서 찾기’, AI는 ‘근거를 읽고 설명’, 프론트엔드는 ‘질문과 출처를 보여주는 화면’이라는 역할이 결정됩니다.

강의 스케치 2 — 내 컴퓨터 안에서 Python/Node, SQLite, AI API, HTML/CSS/JS, Electron을 조합하는 관점

localhost:8000은 “내 컴퓨터의 8000번 문에서 기다리고 있는 프로그램”이라고 생각하면 쉽습니다. Python으로 웹서버를 실행하면 그 서버가 8000번 포트에서 기다리고, 브라우저가 그 주소에 접속해 화면을 받습니다.

이 구조는 인터넷 연결 없이도 가능합니다. 예를 들어 Python + SQLite + HTML로 문서 검색기를 만들고, 내 PC에서만 사용할 수 있습니다. 사용자는 브라우저를 보지만 데이터와 서버는 모두 내 컴퓨터 안에 있습니다.

API는 “남이 이미 만든 기능을 빌려오는 문”입니다

바이브코딩에서 가장 먼저 익혀야 할 습관 중 하나는 “직접 만들기 전에 API가 있는지 찾는 것”입니다.

내가 지도 서비스를 만들고 싶다고 해서 전국 도로 데이터를 직접 수집할 필요는 없습니다. 날씨를 보여주고 싶다고 기상 관측소를 만들 필요도 없습니다. 법령을 검색하고 싶다고 법령 전체를 매번 긁어올 필요도 없습니다. 이미 누군가가 데이터를 정리해 API로 제공한다면 그 통로를 이용할 수 있습니다.

API는 보통 “요청을 보내면 정해진 형식의 결과를 돌려주는 약속”입니다. 예를 들어 GET /weather?city=Seoul 같은 요청을 보내면 JSON으로 온도와 날씨가 돌아옵니다. 내 프로그램은 그 JSON을 받아 화면에 보여주거나 AI의 근거로 사용할 수 있습니다.

XML·JSON·CSV·SQLite·JSONB는 서로 다른 그릇입니다

“무엇이 제일 좋은가?”가 아니라 “어떤 데이터를 어떤 방식으로 찾을 것인가?”에 따라 고릅니다.

형식쉽게 말하면잘 맞는 경우
XML태그로 계층과 의미를 표시RSS, 법령, 문서 구조, 표준 교환
JSON키-값으로 구조화된 데이터API 응답, 웹앱, AI 컨텍스트, 유연한 구조
CSV엑셀처럼 행과 열이 있는 표사람이 먼저 검수, 단순 데이터 교환
SQLite파일 하나로 동작하는 SQL DB로컬 검색, 교육 실습, 개인 도구
PostgreSQL JSONBJSON을 DB 안에서 구조적으로 저장·검색웹서비스, 유연한 스키마, Supabase

예를 들어 법령 조문은 계층이 분명하므로 XML이 자연스럽습니다. API와 주고받는 데이터는 JSON이 편합니다. “먼저 사람이 확인한 뒤 DB로 넣고 싶다”면 CSV가 좋습니다. 로컬에서 빠르게 SQL 검색을 하고 싶으면 SQLite가 아주 편합니다.

한 프로젝트에서 여러 형식을 함께 써도 됩니다. 원본은 XML, 검수는 CSV, 실행용은 SQLite, 웹 API 응답은 JSON처럼 역할을 나누면 됩니다.

정확한 구분 SQLite에 PostgreSQL의 JSONB 타입이 그대로 있는 것은 아닙니다. SQLite에서는 보통 JSON 문자열을 TEXT에 저장하고 JSON 함수를 사용합니다. Supabase는 PostgreSQL 기반이라 JSONB를 직접 사용할 수 있습니다.
같은 데이터를 여러 그릇으로 만들어도 됩니다

원본 문서를 XML로 구조화하고, 사람이 확인하기 위해 CSV를 만들고, 실제 검색 속도를 위해 SQLite로 넣고, 웹 화면에는 JSON으로 보내는 식의 조합이 흔합니다. “한 번 JSON을 선택했으니 끝까지 JSON만 써야 한다”는 규칙은 없습니다.

예를 들어 직원 이름, 부서, 날짜를 찾는 데 임베딩 검색을 쓰는 것은 오히려 복잡할 수 있습니다. 이런 것은 SQL이 정확합니다. 반대로 “표현은 다르지만 의미가 비슷한 정책 문장”을 찾고 싶으면 임베딩이 유리할 수 있습니다.

실무에서는 하나만 고집하지 않고 SQL 필터 + BM25 키워드 검색 + 필요 시 임베딩처럼 하이브리드로 조합하기도 합니다. 중요한 것은 “가장 단순한 방식으로 먼저 성공시키기”입니다.

추천 실험 순서 파일 직접 읽기 → JSON/Fuse.js → SQLite FTS5/BM25 → 필요하면 임베딩. 처음부터 벡터DB를 넣으면 디버깅할 요소가 불필요하게 늘 수 있습니다.
어떤 검색을 먼저 선택할지 아주 쉽게 판단하는 법
  • 정확한 값 찾기: 이름·부서·날짜·금액 → SQL
  • 문서 속 단어 찾기: 규정, 지침, 기사 → FTS5/BM25
  • 작은 JSON을 브라우저에서 검색: Fuse.js
  • 다른 표현인데 의미가 비슷한 문장: 임베딩

한 질문에서도 두 방식을 함께 쓸 수 있습니다. 먼저 SQL로 “2026년 문서”만 좁힌 뒤 그 안에서 BM25로 관련 문장을 찾으면 검색 범위가 작아지고 결과도 설명하기 쉽습니다.

강의 스케치 4 — AI가 MCP 서버에 연결되고, 서버 안의 도구가 API·문서·CLI·DB를 호출하는 개념
